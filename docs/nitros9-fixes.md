# Fixes for NitrOS9 main

Problems in NitrOS9 `main` found while building devsys. `~/projects/wild/main/nitros9`
is kept a pristine copy of upstream `main`: don't change it. Each fix goes on its own
branch of the owner's fork `jfed6000/nitros9` (a working clone of the fork, never the pristine copy,
whose origin is `nitros9project/nitros9`) and is submitted upstream as a pull request from there, when
the owner decides to. Nothing is committed to `nitros9project/nitros9` except through a PR. Until
then devsys lives with them.

| # | Found | Where | Problem | Fix | Status |
|---|---|---|---|---|---|
| 1 | 2026-10-12, K2 card 4 (D47) | `lib/alib/fgets.as` `FGETS_NOCR` | On an error the routine's `puls d,x,pc` puts the caller's old B back over the error code from `I$ReadLn`; carry stays set. `grep` then misses `E$EOF` and exits with a leftover byte (`ERROR #115` after a match, 110 without, in the shell). Affects `/dd/CMDS/grep` too | On the error path `stb 1,s` (B into the saved D) before `puls d,x,pc`; tried 2026-10-12: grep exits 0, a missing file still gives 216, MAME rehearsal clean, lwdiff on main unchanged otherwise (grep 383 → 387 bytes) | open, no PR |
| 2 | 2026-10-12, boot disk rebuild | `rules.mak` (library rule, line 124) | A library is built with `lwar -c $@ $?`: after one member's source changes, the library is re-created holding only that member (`libalib.a` 16,289 → 173 bytes) and the next link fails (`PUTS` not found). Programs aren't relinked when a library they use changes | Build the library from all its members (`$^`), and make each linked program depend on its libraries | open, no PR. devsys workaround: delete `boot/wildbits/l2/.lib/libNAME.a` and the `.mods/` programs using it, then `make` |
| 3 | 2026-10-12, K2 card 4 | `level1/cmds/grep.as` | `-n` counts only lines at least as long as the pattern (`subb <pattlen` / `bmi ReadIn` come before the count), so line numbers are low (README line 52 counted as 44). On the 6809 (K2 and MAME) the printed number is stranger still (`0040::`, `0040=:`), see DESIGN §10 | Count each line before the length test | open, no PR; numbering on the real CPU not yet understood |
| 4 | 2026-10-12, boot disks after pulling `9062f685` | `rules.mak` / recipe makefiles | A module or library member depends only on its own source, not on the defs it includes (`use defsfile`, `wildbits.d`): after `defs/wildbits.d` changed, `make` rebuilt nothing that uses it (`libwildbitsl2.a` stayed 58,080 bytes; built clean it is 60,858) | Generate include dependencies (lwasm `--dependnoerr`/`--depend` into `.d` files) or make objects depend on `defs/*` | open, no PR. devsys workaround: after pulling `main`, `rm -rf .mods .obj .lib` in `boot/wildbits/l2` before `make` |
| 5 | 2026-10-13, step 17 (D51) | `level2/modules/kernel/ffreehb.asm` (`F$FreeHB`, used by `F$MapBlk`) | On the F256 a process whose module doesn't reach the top slot (a module ending below `$E000`, e.g. 15,617 to 16,384 bytes, which NitrOS9 maps at `$A000`) has slot 7 marked `DAT.Free`, and `F$MapBlk` hands out the highest free slot: `$E000`. The block mapped there covers the system's page at `$FE00` (vectors), and the machine hangs at the next interrupt. Found when the banked dco68 (15,866 bytes) hung in MAME on its first window. The CoCo 3 never meets it (its hardware keeps the constant page at `$FE00`) | `F$FreeHB` already treats block 7 as occupied under `IFNE picothing` ("is this block 7 (the kernel slot)?"); do the same for wildbits (or every port without a hardware constant page) | open, no PR. devsys workaround: dco68 checks at start that its code reaches `$E000` (`bank.c` `newblock`) and stays at most 15,616 bytes; `os9run.py` models the hazard |
| 6 | 2026-10-16, packaging question (D68) | `lib/kreiderclib/` | A second copy of the C library, and an unusable one: 130 files made by Os9disasm from an old Kreider `clib.l` (labels `L0004`, `B0000`), added 2013, built by no makefile since 2014 (`Makefile.old` removed). `harness/kreiderdiff.py` assembles the 128 `.as` files with las (rules.mak's object options, `export`) and compares them with devsys's `clib.l`/`sys.l` (from the sources, D52): **99 identical**; **11 broken by the disassembly**: data after the code lost (`errmsg`'s `"%s: "`, `pflinit`'s `"-2147483648"` decoded as `blt`, strings in `adump`, `getopt`, `popen`, `prof`, `pwent`, `pffinit`, `utime`), entry points turned into constants (`sleep equ *-2`, `rewind`, `o2utime`: a call goes to `$0004`); **a real bug**: `cldiv` has `inc 1,s` where the sources' fix (`*+crk+`) has `com 1,s`, so a negative `long` divided by a negative `long` has the wrong sign (`-10L / -2L` = `-5`: `printf("%ld", ...)` of `-10/-2, -10/2, 10/-2, 10/2` prints `-5 -5 -5 5` with its `cldiv` linked in, `5 -5 -5 5` with ours, on `os9run.py`); 18 differ otherwise (older sources: `utime`, `getopt`, `prof`; devsys's D43 `scale` fix and D67 `putc`/`puts`/`printf`; encodings). As a library it can't link: no file exports anything, and with `export` 149 labels are defined in several files (`L0008` ×14: "symbol already defined"). Missing: `scanf`/`sscanf`/`fscanf`, `qsort` (an RMA `.a`), trig/log/`sqrt` (`clibt.l`), `ldexp`/`frexp`, `_ludiv`/`_lumod`/`_lushr` (which the compiler calls), `localtime`/`mktime`/`gmtime`, `cstart`, `sys.l`; `signal` is named `_sigint`, `index`/`rindex` only `strchr`/`strrchr` | Remove `lib/kreiderclib`, or replace it with devsys's `clib/` (sources, makefile, `cstart.r`, `clib.l`, `clibt.l`, `sys.l`) when devsys goes into the wildbits build | open, no PR. devsys uses only its own `clib/` (D68) |
