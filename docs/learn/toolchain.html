How source code becomes a running program

Compilers, assemblers, linkers, object files and modules, explained with real files from your own trees: a C program compiled by DCC, the object file RMA made from it, and a module built by lwasm.

CHAPTER 01The pipeline

A program goes through several separate tools before the 6809 can run it. Each tool reads one kind of file and writes another. Here is a C program on its way to becoming an OS-9 command:

Compilerdcc68Translates C into assembly language. This is where the language rules live.
Optimizerdco68Rewrites the assembly to be smaller and faster, using patterns.

LinkerrlinkJoins object files and library pieces into one program and fills in the addresses each piece needed from the others.

Why so many separate programs? On a 6809, a program can address only 64K. One program that did all six jobs wouldn't fit, so each job became its own program, passing files to the next. That's also why a C build creates temporary files. Modern compilers like gcc still use the same stages; they just hide them.

Hand-written assembly skips the first three steps and starts at the assembler. And as chapter 3 explains, some assembly skips the linker as well.

These are the names in CoCoC, the C compiler as you had it. This project replaces the last two stages with its own forks, under their own names: las instead of rma, and llink instead of rlink (chapter 6 explains the second). The first three keep their names.

CHAPTER 02What the 6809 actually runs: a module

Every program, driver and descriptor on NitrOS9 is a module: a block of bytes with a fixed header at the front and a checksum at the end. The OS refuses to run anything that isn't a valid module. Whichever tools you use, a module is always the end product.

Here is a complete, real one. This program prints “Hi”. I assembled it with lwasm using the Level 2 wildbits defs:

         mod   eom,name,tylg,atrv,start,size
count    rmb   1                  ← variables: these reserve space,
         rmb   250                ←   they produce no bytes
size     equ   .                  ← total data size = 251
name     fcs   /hello/
         fcb   edition
msg      fcc   /Hi/
         fcb   C$CR
start    leax  msg,pcr            ← address of msg, relative to here
         ldy   #3
         lda   #1                 ← path 1 = standard output
         os9   I$WritLn
         clrb
         os9   F$Exit
         emod
eom      equ   *

    Three things to notice

    The header describes the module. 87 CD marks the start of a module. Then: total size, where the name is, type ($11 = program, 6809 code), attributes ($80 = re-entrant, meaning one copy in memory can serve several processes), where execution starts, and how much data memory the process needs. The mod line in the source supplies all of it.

    Variables are not in the module. count and the 250-byte buffer produced no bytes at all. They only set the data size ($00FB = 251) in the header. When the program starts, OS-9 gives the process a fresh 251-byte data area and points register U at it. The code reaches its variables relative to that register. This is how several processes can share one copy of the code: each gets its own data.

    The code doesn't care where it's loaded. leax msg,pcr assembled to 30 8C FA: “X = this instruction's address minus 6”. No fixed address appears anywhere. This is called position-independent code, and OS-9 requires it, because the OS decides where a module goes in memory.

    os9 I$WritLn became 10 3F 8C: the SWI2 instruction, followed by the number of the system call. That's all a system call is. The defs file gives I$WritLn its number.

    Two location counters

    An assembler keeps a location counter: the address the next byte will go to. Inside a module there are two. * counts code bytes, and . counts data bytes. Both start at 0 at mod.

    In hello, count rmb 1 and rmb 250 advance only ., from 0 to 251, so size equ . gets 251, the data area size the header needs. Instructions and fcb/fcc advance *, so eom equ * at the end gets 41, the module's total length. Two counters let one file describe two separate things: the bytes of the module, and the layout of the memory OS-9 will give the process.

    Outside a module there's only one counter, and rmb still writes no bytes. That's how the defs use org 0 followed by a list of rmbs to give names to the offsets of a structure, without producing any output.

    The header check byte

    Byte 8 of the header protects the 8 bytes before it. XOR them together, then flip every bit. XOR compares bits: the result bit is 1 where the two inputs differ.

    ByteRunning XOR
    8787 · 10000111
    CD4A · 01001010
    004A · 01001010
    2963 · 01100011
    0063 · 01100011
    0D6E · 01101110
    117F · 01111111
    80FF · 11111111

    Flip every bit of FF and you get 00, the check byte in hello. OS-9 checks it the other way round: XOR all 9 bytes and the answer must be FF. It's a quick test that a header is real before OS-9 trusts any of its fields.

    The CRC

    The last 3 bytes protect the whole module. A CRC (cyclic redundancy check) runs every byte through a 24-bit shift register: the register starts at FF FF FF, each byte is mixed in by shifting and XORing at fixed bit positions, and at the end every bit is flipped. A single wrong bit anywhere changes the result, and so do most combinations of errors.

    For hello the register ends at CA 6D D8. Flipped, that's 35 92 27, the 3 bytes emod appends. And there's a neat property: run the same calculation over the whole module, CRC included, and the answer is always 80 0F E3, whatever the module contains. That's how OS-9 checks a module when it loads it: it doesn't need to find the stored CRC, it just checks that the total comes out to that constant.

    las computes the CRC while it writes the module in pass 2, byte by byte, so it never has to hold the module in memory. lwasm builds the whole module image first and then computes it.

    CHAPTER 03Three source formats, and why

    Your NitrOS9 and compiler trees contain assembly written three different ways. All three end up as the same kind of module from chapter 2. What differs is how they get there, and the difference is whether a linker is involved.

    Module .asm

    The source writes the module header itself. The assembler outputs the finished module. No linker.

     atrv,start,size

    e.g. gfxstatus.as, lib/alib

    The history behind it

    Around 1980, Microware shipped OS-9 with asm, which builds a module directly from one source file. That's the module format. When they added a C compiler, they needed to compile files separately and pull routines from a library, which asm can't do. So they wrote RMA (the Relocating Macro Assembler) and rlink, with their own object file format, ROF. That's the RMA object format.

    Decades later, lwtools (lwasm + lwlink) became the cross-assembler for NitrOS9. It reads the old module format so the existing sources still build. For linked programs it invented its own object style (section) and file format (LWOBJ) instead of copying Microware's. That's the third format.

    Same idea, two vocabularies

    The two object styles express the same ideas with different words:

    Variables go heresection bssvsect
    Program starts herelabel named __startlast field of the psect line
    Other files may use this nameexportlabel: (trailing colon)

    Library.a (lwar).l

    The two binary formats can't be mixed: lwlink can't read ROF and rlink can't read LWOBJ.

    Which one is better?

    Neither. They suit different jobs.

    The object formats win when code is shared or split up: C programs, libraries, big applications. You link only the library pieces you use.

    The module format wins when exact layout matters. A device descriptor is a table of bytes at fixed offsets. A driver must start with an entry table right after the header. With mod you write exactly the bytes you want, in order, and every header field is visible in the source. It's also one step instead of two, which matters when the build runs on a 6809.

    If you use a whole library file in a module, you get the whole library. If you link against it, you get only the pieces you call. That's the main practical difference.

    How las tells them apart

    las assembles all three. It reads RMA sources the way RMA does, and module and lwasm-object sources the way lwasm does (the two dialects of chapter 4). You can name the dialect with --rma or --lwasm, but you don't have to: the boxes above show each format announcing itself in its operation field. Before it starts, las reads the source for the first line whose operation is one of three words:

    First one foundDialectOutput
    psectRMAROF object, for llink
    sectionlwasmROF object, for llink (lwlink's layout)
    modlwasmthe finished module
    none of themlwasmraw bytes (fonts, patterns, pictures)

    Why read ahead, and not just switch when it meets the word? Because the dialect changes how every line is read, and the first lines of echo.asm come before its mod: they use the defs, which are read differently in each dialect. So the choice has to be made before line 1.

    Why does "none" mean lwasm? RMA puts code and data only inside a psect. Outside one it says "bad mnemonic", so a file without psect can't be an RMA program. In your NitrOS9 tree, the 28 such files are all lwasm data files like level2/sys/stdfonts.asm.

    Checked on every source we test with: 262 NitrOS9 sources decide by section or mod, the other 28 fall back, and all 252 hand-written RMA sources have psect. With the flag left out, all 290 NitrOS9 sources give the same bytes as with it. NitrOS9 builds still pass their --pragma= list, because those options are choices of that build, not lwasm's defaults.

    CHAPTER 04How an assembler works

    An assembler's basic job is a lookup: ldd #3 → CC 00 03. The hard part is labels. Look at this:

             lbsr  printit      ← where is printit? Not seen yet.
         ...
printit  lda   ,x+

    When the assembler reaches the lbsr, it hasn't seen printit yet, so it can't know the address. This is a forward reference. The standard answer is to read the source twice.

    PassWhat it does
    Pass 1Walks the whole file counting bytes, without writing anything. Every time it meets a label, it records the name and its address in the symbol table.
    Pass 2Walks the file again. Now every label is in the table, so it writes the real bytes.

    The two passes must agree on every address. If an instruction comes out a different size in pass 2 than in pass 1, everything after it shifts and the assembler reports a phasing error. That's why ifp1 / use defsfile / endc appears at the top of so many files: read the big defs file in pass 1 only, since its symbols are already in the table for pass 2.

    Choosing instruction sizes

    Some instructions come in several sizes. leax msg,pcr loads the address of msg as a distance from the current instruction. If the distance fits in 8 bits (−128 to +127), the instruction is 3 bytes: 30 8C FA. Otherwise it needs 16 bits and is 4 bytes: 30 8D FF F9.

    For a label defined earlier, the assembler knows the distance and can pick the short form. For a label defined later, a forward reference, it doesn't know the distance yet in pass 1. A two-pass assembler has to guess, and the safe guess is the long form, because whatever it picks in pass 1 it must keep in pass 2, or every address after it would move. That would be a phasing error.

    RMA always uses the long form for ,pcr unless the source asks for the short one with <, even for backward references. lwasm doesn't guess. It keeps a line whose size it can't decide yet unsettled, and comes back to it. Its rule, read from its source (pass3.c, pass4.c, insn_indexed.c), has three parts:

    1. Known distance. If every line between the instruction and its target is settled, the distance is known exactly. The short form is used if it fits in −128 to +127.
    2. Worst case. Otherwise lwasm counts every unsettled line at its longest size. If the distance still comes out within ±100, the short form is safe whatever happens, so it is chosen now. The margin of 27 is deliberate caution. One quirk: lwasm only records a longest size for ordinary instructions, not for leax/leay/leau/leas, so an unsettled lea in between rules this step out.
    3. Stuck. Some lines can never be settled while assembling: jsr extfunc, or leax buffer,u where buffer is in a relocatable section, because the value only exists after linking. When nothing more can be settled, lwasm forces the first unsettled line, in source order, to its long form, and tries the rest again.

    Sizes only ever shrink as lines settle, so a worst case only gets better. That's why this always finishes, and why the order lwasm looks at lines doesn't change the answer, except in the forced step.

    A real case from gfxstatus, where the target is 77 bytes ahead:

         leay  cluttxt,pcr     ← 77 bytes to cluttxt: fits, but…
     lbsr  tobuf
     leax  clutdata,u      ← clutdata is in bss: never settled, and a lea
     …
cluttxt fcs "CLUT0 FIRST AND LAST 20 VALUES: "

    The distance isn't known, because leax clutdata,u is unsettled, and the worst case is ruled out because that line is a lea. So lwasm ends up forcing leay to 16 bits, though 8 would have fitted. To produce the same bytes, las has to copy the rule, quirks included. "Shortest that fits" would get this line wrong.

    How las does it

    las is a two-pass assembler, and changing that would be a big rewrite. Instead it makes a trial run first. Before pass 1 it splits into two processes (on Linux, fork()). The copy runs pass 1 with every ,pcr long, writing down each one and each line lwasm would leave unsettled. At the end it replays lwasm's rule on those notes, sends back one answer per ,pcr (short or long), and exits. The original, which has done nothing meanwhile, then assembles for real with those answers. Its pass 1 and pass 2 agree on every size, so the phasing check still guards the result. With it, every module file matches lwasm's byte for byte.

    One bug on the way is worth knowing about. After a fork(), both processes share an open file's position. The trial read the source to the end, so the real pass 1 started at end-of-file and saw nothing. It needed a rewind(). Separate copies of memory don't mean separate copies of everything.

    That was the first design. Since step 19 (chapter 11, "The trial without a child") there is no second process: pass 1 itself is the trial, and settling passes (below) correct the values once the sizes are decided.

    Local labels

    Every routine needs a loop label, and naming them all differently gets tedious. lwasm lets a name containing @ be local: loop@ in one routine and loop@ in the next are different symbols. The interesting part is where one scope ends and the next begins. For lwasm the answer is surprising: a blank line ends it. A new ordinary label does not.

    A    nop
l@   nop          ← scope 0
     bra  l@
B    nop          ← still scope 0: a second l@ here is an error
                  ← blank line: scope 1 starts
l@   nop
     bra  l@

    A macro expansion gets a scope of its own and then hands the caller's scope back, so a label on the line that calls a macro is still visible afterwards. las stores local names with their scope number attached: its symbol table lists l@~0, l@~1 and so on.

    Conditions across two passes

    Include files often protect themselves from being read twice. os9.d starts like this:

             IFNE  OS9.D-1      true while OS9.D is undefined (0)
OS9.D    SET   1
         ...the whole file...
         ENDC

    This is an include guard. In pass 1, OS9.D is undefined, so the test is true and the file is read. But a two-pass assembler starts pass 2 with everything pass 1 learned, including OS9.D = 1. Now the guard says “already included”, and pass 2 silently skips the whole file. Every address after it shifts, and the passes disagree: phasing errors.

    The fix comes from how lwasm works. It decides each condition once, when it first reads the line, but works out values later, when everything is known. So las records the outcome of every condition in pass 1, one bit each, and replays the same outcomes in pass 2. Both passes then read exactly the same lines, while values still use the final symbol table. That second half matters too: a forward reference to a set symbol gets its final value in lwasm, and my first attempt at a fix (resetting set symbols before pass 2) got that wrong. Testing both behaviours against lwasm is what caught it.

    Fixing the guard also exposed errors that had been there all along. RMA reports errors only in pass 2, and pass 2 had been skipping the defs, so 171 files hid a real problem (0x hex numbers, which RMA didn't support) until the passes agreed.

    When a size comes later: settling

    Your multiterminal vtio work added this to defs/wildbits_vtio.d in NitrOS9 main:

    386  gr.SprTbl   rmb   G.TermMax*8   ; one row per terminal
...
527  G.TermMax   equ   9             ; Maximum terminals (0-8)

    The rmb reserves space using a value that is only defined 140 lines later. lwasm doesn't mind: it keeps making passes over the file until no value changes, so gr.SprTbl ends up 72 bytes long. A two-pass assembler can't. In pass 1, G.TermMax isn't known, so las counted the rmb as 0 bytes, and every label after it got an address 72 too low. In pass 2 the count is known, every one of those labels moves, and each move is a phasing error. A small file shows it. This is the old las's listing:

    00003 0002            b        rmb   N*8
*** error - phasing error ***
00004 004a            c        rmb   1
00005 0009            N        equ   9

    Look at the addresses: pass 2 already printed c at $4A, which is right (2 + 9×8). Pass 2 corrects each label it reaches and then complains that it had to. So the cure was already in the code. las now notes in pass 1 when a count (rmb, org, fill) uses a symbol it hasn't reached yet. If it noted one, it runs pass 2's code once more before the real pass 2, as a settling pass: it writes nothing, lists nothing, reports nothing, and only counts how many values moved. When nothing moves, the real pass 2 runs as always, phase check included. A file without such a count pays nothing. In main, 16 files take one settling pass: the vtio family and wildbitsl2, the constants library every object program is linked with.

    Assembling main found two more things. grfdrv256 says tfr 0,dp: lwasm reads 0 as a register, the 6309's zero register (register code $C), so the instruction is 1F CB and clears DP. It works on a 6809 too. las learned it. In its register table the digit is stored as '0' & $DF, because las uppercases a character by clearing bit 5, and that changes digits too.

    The other was quieter. The ,pcr trial (above) keeps its notes in the same 8K blocks as the symbols, at most 15 of them. In main, krnp2 gave it 2,560 labels to note, mostly the defs' structure offsets, and it ran out. A failed trial isn't an error: las prints one warning and uses long offsets. The only trace was krnp2 coming out 2 bytes longer than lwasm's. The notes were there to tell apart labels in different lwasm sections, and a module has none. So now a code label is marked by one spare bit in its own symbol record, and only labels inside a section are listed. The test harness now names any file whose trial failed.

    Same symbols, different meaning

    The two assemblers mostly agree on expressions, but not entirely. The biggest difference is operator precedence, which operator is applied first:

    ExpressionRMAlwasm
    2+3&62+(3&6) = 4(2+3)&6 = 4
    A+B&C& before ++ before &
    1024^2error: ^ is only a prefix (complement)1024 XOR 2 = 1026
    $F0|$0Ferror: no |$FF

    The first row happens to give the same answer either way, which is exactly why this kind of difference is dangerous: most expressions agree, and the ones that don't give a wrong number, not an error. las uses lwasm's precedence in lwasm mode and RMA's otherwise. Names follow the same pattern: NitrOS9 builds with case-insensitive symbols, so HW.PAGE in one file finds HW.Page in the defs.

    Structures: names for offsets

    A program often keeps records in memory: several values that belong together, laid out the same way each time. To reach a value, the code adds its offset (its distance from the record's start) to a pointer. The old way to name offsets is org 0 followed by rmb lines, which is how defs/os9.d describes a process descriptor (ORG 0, then P$ID RMB 1, P$PID RMB 1, …). lwasm has a tidier way, struct, and your level1/cmds/minted.asm (the text editor) uses it for its undo list:

    undo_item struct
previous  rmb 2
next      rmb 2
scrline   rmb 2
cx        rmb 1
cy        rmb 1
key       rmb 1
topstr    rmb 2
          endstruct

    This reserves no memory. At endstruct it defines a symbol for each field, named struct.field, with the field's offset: undo_item.cx is 6 and undo_item.key is 8. It also defines sizeof{undo_item}, here 11. The code then reads like a C program's p->key:

    1322 8e000b              ldx   #sizeof{undo_item}
13a3 a608       @last    lda   undo_item.key,x

    The point is the prefix. A few lines further down, minted has its own variables called cx, cy and key, at data offsets 1, 2 and 4. With org/rmb, the field cx and the variable cx would be the same symbol defined twice. Inside a struct the field labels never become symbols of their own, so the two don't meet.

    A struct's name can also stand where an operation goes. Inside another struct it nests one (pos pt gives item.pos.x). Elsewhere it reserves one instance: p1 pt in a bss section reserves sizeof{pt} bytes, like rmb, and defines p1.x and p1.y as variables at p1 plus the offsets.

    las got all of this on 2026-10-07 (las/lwstruct.c). It was the last lwasm feature the NitrOS9 build needed: with it, all 200 module sources match lwasm byte for byte. We checked the parts minted doesn't use against lwasm too: nesting, rmd/rmq fields, and instances in bss and data sections, linked with lwlink and with rlink --lwlink. One case is different on purpose. An instance inside a module makes lwasm write a module whose size field doesn't match its bytes, so las reports an error there and suggests rmb sizeof{name}.

    Two dialects in one assembler

    las now speaks two dialects. In RMA's it behaves like RMA, which RMA's own sources and the C compiler's output rely on. In lwasm's (--lwasm, or detected from the source as chapter 3 shows) it behaves like lwasm: the local labels, condition replay, operators and the other differences above. Keeping them separate means each set of sources keeps the meaning it was written for, and the regression test can keep guarding RMA behaviour while lwasm behaviour is built up.

    Reading a listing

    This is part of RMA's listing for the C example from chapter 7:

    00008 0000 3440       add:     pshs  u
00010 0005=17fff8              lbsr  _stkcheck
00022 0020 8dde                bsr   add
00024 0024 eda90000            std   total,y
00028 0030=17ffcd              lbsr  printf

    Columns: source line, address, bytes produced, then the source. The = after the address means “this instruction uses a name from another file”. RMA can't know where printf will end up, so it writes a placeholder and leaves a note for the linker. That note is what the next chapter is about.

    bsr add → 8D DE needed no note: add is in the same file, $22 bytes back, so the assembler knew the distance ($DE = −34).

    Files bigger than memory

    The assembler never holds the whole source file. It reads one line into a 256-byte buffer, assembles it, and reads the next. At the end of pass 1 it rewinds the file and reads it all again for pass 2. use files are read the same way while the outer file waits. Macro definitions go to a work file on disk (rma.tmp) and are read back each time the macro is used.

    Output streams too. Pass 1 has already worked out every size, so pass 2 can write the object file's header first and then each line's bytes straight into their place in the file, seeking between the code and data regions as the source switches between them. At the end it goes back to patch one header byte (“assembled without errors”) and writes the reference lists.

    Only a few things must stay in memory until the end:

    Kept in memoryGrows with
    Symbol tablethe number of names, including about 1,600 from the defs
    Reference lists, the object file's “names needed” and “fixups”how often the code uses outside names or needs patching
    Macro names and their positions in the work filethe number of macros, not their length

    So a long program with few names fits easily. What runs out on a 6809 is names and references, not lines. That's why chapter 9 is about the symbol table.

    CHAPTER 05Inside an object file

    An object file is machine code that isn't finished yet. Alongside the code it carries lists: names this file provides, names it needs from elsewhere, and places in the code the linker must patch. Here is the real sum.r that RMA made from the C example, all 158 bytes:

      The four lists

      Header (blue). Sizes: 2 bytes of variables, 59 bytes of code. Notice the type and language bytes are 00 00: this file isn't a whole program, so it doesn't say what kind of module it'll become. Another file (the C startup, cstart.r) supplies that.

      Names this file provides (gold). total at offset 0 in the data area, main at code offset $0E, add at code offset 0. Each has a flag byte saying whether it's code or data.

      Names this file needs (red). printf, used once at code offset $31. _stkcheck, used twice, at $06 and $14. Those offsets point exactly at the placeholder bytes behind the = marks in the listing.

      Local fixups (red, last entry). Code offset $26 is std total,y. The variable total is in this file, but its final place in the data area depends on how many variables other files have. So the linker must adjust this one too.

      An object file is a contract: “here are my pieces, here's what I need, here's where to patch me once you know.”

      CHAPTER 06What the linker does

      rlink cstart.r sum.r -l=clib.l -o=sum does this:

      StepWhat happens
      1. CollectRead every object file listed. Note every name provided and every name needed.
      2. ResolveFor each name still needed (printf, _stkcheck), search the libraries. Take the library piece that provides it. That piece may need more names (printf needs output routines), so repeat until nothing is missing. Anything still missing is an “unresolved reference” error.
      3. Lay outPlace all the code pieces one after another, and all the variable pieces one after another. Now every name has a final offset.
      4. PatchGo through every fixup and write the real offset into the placeholder bytes.
      5. WrapWrite the module header (type, size, entry point, data size) and the CRC. Out comes a module just like chapter 2's.

      Libraries are bundles of members

      A library like clib.l is many object files stuck together. Each one is a member. In step 2 the linker takes whole members, never parts of one. If one member held 20 routines, calling one would bring in all 20. That's why library sources are split one routine per file: lib/alib has bin_hex.as, bin_dec.as, asc_bin.as, and so on.

      Why the module format needs no linker

      A mod/emod file has no needed names (everything comes from the file plus its use includes) and no fixups (the code is position-independent and the data is reached through U). With nothing to resolve or patch, the assembler can do step 5 itself.

      The extra tables are for Microware's C compiler. A C program's start-up code (cstart) reads them at run time to copy initial values into the data area. Assembly programs built by lwlink don't need them. Both layouts are valid OS-9 modules; the operating system only cares about the header and the CRC. But they can never be byte-identical, so las's rlink got a second mode, --lwlink, that writes lwlink's layout.

      Header values differ too. rlink takes the module type, attributes and stack from the main file's psect line. lwlink takes them from a special section called __os9, and uses defaults (program, 6809 code, re-entrant, no extra stack) when there isn't one.

      Choosing library members

      Microware's rlink reads each library once, from start to end, taking a member if it defines a name something still needs. That fails here:

      libalib.a:  ... fputs ... puts ...
program needs PUTS  →  take puts
puts needs FPUTS    →  but fputs was already passed

      lwlink keeps going round until a full pass adds nothing new, so it finds fputs on the second pass. And it lays the members out in the order they sit in the library, not the order it found them. The order matters: it decides where every routine ends up, and so every address in the module. las's rlink does the same in --lwlink mode: it decides the members up front, exactly as lwlink would, and then links them in library order.

      The order between files has a twist too. lwlink places sections by name first, in the order its script lists them (code, .text, data, .data), and by command-line position second. NitrOS9 links with the libraries first: lwlink -lwildbitsl2 -lnet -lalib dw.o. The net library uses section code, like the programs, so a net routine lands before the program's own code. The alib library uses .text, so its routines land after. Same command line, opposite results, purely because of a section's name. las records each file's section in its object (as the constant __lwsec), and rlink sorts by the same rule.

      One linker, two layouts, and a new name

      Our fork of rlink is called llink since 2026-10-08. The reason is practical. Your PATH has ~/projects/bin/rlink, the original, which keeps only 9 characters of a name. The dcc driver runs its linker by name, so with both called rlink, a C program built with our dcc on Linux could quietly link with the old one. On the F256 the two can't even sit side by side in /dd/CMDS. las never had this problem, because it doesn't share a name with rma. llink pairs with it.

      The same day, llink learned to choose between the two layouts above by itself, so --lwlink is now optional. It uses a clue las already leaves: every object it makes from lwasm-style source exports __lwsec. Before linking, llink reads the input files' headers and global names until it reaches the mainline, the one module that has a module type (a program's __start file, or a C program's cstart.r). If the mainline exports __lwsec, it uses lwlink's layout; if not, Microware's. Measured on every object the tests make: all 19 lwasm-style mainlines have it, and none of the 9 Microware ones nor any of the 677 modules in CoCoC's libraries do.

      Why the mainline, and not any object at all? Because one lwasm library member has no __lwsec: wildbitsl2's constants-only object, which has no code section to rank. A rule based on members would trip over it. The mainline is the module that sets the program's header anyway. --lwlink and --mw still force a layout, for the rare link that needs it.

      Values only the linker knows

      Many NitrOS9 object-format files never include the defs. Names like F$Exit or Prgrm are simply undefined while assembling, so they become external references, and the linker fills in the numbers from a library that exports the defs (wildbitsl2).

      The two object formats differ in what they can ask of the linker. lwasm's can store a whole expression: “take Prgrm, add Objct, multiply by 256”, or “the complement of Carry”. ROF can only say “add (or subtract) this symbol's value here”. So ldd #(Prgrm+Objct)*256 has no way to be written in ROF.

      The solution is to let the assembler see those constants too. las --defs=wildbitsl2.r reads the constants that library exports. References to them still stay external, so the instructions keep the sizes lwasm chose and the linker fills them in, except where ROF can't express the expression. There, las uses the value itself. The result is the same bytes the linker would have produced.

      A value too big for its place

      play contains lda #MIDIMMC_DEVICE_ALL*256+$09. MIDIMMC_DEVICE_ALL is $7F, so the value is $7F09, which can't fit in lda's one byte. lwasm can't see that: to it the value is unknown, so it just records an 8-bit reference (FLAGS=01 … @ 05A1), and lwlink later keeps the low byte, $09. Once --defs made the value known, las reported “value out of range” instead. To produce the same module, las now does what the linker would: for an 8-bit value that came from --defs constants, it keeps the low byte and writes 86 09. The source probably meant something else, but matching lwasm means matching this too.

      It's the RMA object format, with psect, vsect and label: exports. That's why the C toolchain needs RMA and rlink no matter which compiler you use.

      The calling convention. Arguments go on the stack, the result comes back in D. Globals are reached through Y, which the C startup code points at the data area. Hand-written assembly usually uses U for this.

      The optimizer's work. dco68 made two changes. It turned lbsr add into bsr add, a shorter instruction, since add is close by. And it removed ldd total,y, because D already holds the value that was just stored. Small wins like these, made by matching patterns, are all a peephole optimizer does.

      How long can a name be, and why

      Each limit in the chain has its own reason, so here they all are in one place, with what we measured in your trees.

      WhereLimitWhy

      What C89 actually says. The standard sets minimums a compiler must meet, not maximums. For names visible only inside one file it requires 31 significant characters. For external names, the ones the linker sees, it promised only 6, and those could be compared without regard to case. That was a concession to the linkers of the 1980s, which had exactly the kind of limits rlink had. C99 raised the minimums to 63 and 31. Since our linker keeps 63, DCC's external names get all 31 too, which C89 allows because 6 is only the floor.

      Is 31 enough? Measured on CoCoC's C sources (340 files, 5,440 different names), the longest name is 20 characters (NOT_COLON_DEFINITION). Cut to 8 characters, 40 of those names collide with another. Cut to 31, none do. On the assembly side, the longest name in the NitrOS9 defs is 24 characters, and 167 of them collide at 8 (chapter 9). Both limits have plenty of room.

      What a limit costs. With fixed records, a higher limit costs memory on every symbol, which is why the old tools stopped at 8. With records that are only as long as their name (chapter 9), the limit costs nothing until a name actually uses it. That's what made generous limits affordable on a 64K machine.

      Old libraries, new names

      The localtime failure has a second cause. CoCoC's clib.l was built with the 8-character tools, so the library itself calls the function localtim. The same goes for intercep, sdiffere and dozens of others. A compiler that keeps long names asks for localtime, and the library doesn't have it.

      The fix uses a byte that was there all along. Every ROF header records the format version that wrote it: Microware's tools wrote 0, and las writes 1. So rlink knows which objects came from tools that kept only 8 characters, and treats their names the way those tools did. When localtime is wanted and a version-0 module defines localtim, rlink gives that module an alias, a second name for the same address. The map shows both:

           localtim  code 031c
     localtime code 031c

      Between new objects, names still have to match in full. The old rule only applies where the old tools were used. Since step 18 devsys builds its own libraries with whole names (below, "Building the C library ourselves"), so its programs no longer need the aliases. They stay for any old Microware object you link.

      Checking that nothing else changed

      After the change, 59 of CoCoC's C files compiled differently, which was expected. But "expected" isn't checked. The comparison tool (harness/dccdiff.py --names8) splits both outputs into words and accepts a difference only where the new word is longer than 8 characters and the old one is its first 8. All 59 passed, so nothing changed except the names. That's a pattern worth reusing: when you know what kind of difference a change should make, write a test that allows exactly that kind and nothing else.

      The symbol entries use chapter 9's trick. Each keeps the old room for 8 characters, and only a longer name gets a longer entry, so short names cost the same memory on the 6809 as before. And testing under AddressSanitizer turned up the usual suspects: a pointer that was never set, in the code for struct tag x[3]. It had worked only while fresh memory happened to be zero, and one XLisp source crashed the original compiler. It compiles now.

      How the driver knows a pass failed

      dcc itself compiles nothing. It is a driver: it starts each pass as a separate process, waits for it, and looks at the number the pass hands back when it ends, its exit status. 0 means it worked. Anything else means stop: there is no point optimizing code the compiler couldn't finish. Until 2026-10-07 the Linux build lost that number. Here is a file with a missing semicolon, through the old driver:

       dcc68: -o=ctmp.pNeJLM.i ctmp.pNeJLM.m
bad.c:4: *** ; expected ***
errors: 2
 dco68: ctmp.pNeJLM.i ctmp.pNeJLM.m
   rma: -o=bad.r ctmp.pNeJLM.m

      dcc68 found two errors and failed, yet the driver ran the optimizer and the assembler anyway, and reported success. The cause is one line in dcc/DCC/dcc.c: exit(system(cmd)). On Unix, system() doesn't return the program's exit code. It returns a wait status, which packs the code into the second byte (exit code 1 comes back as 256) so the low byte can say whether a signal killed the program. An exit code only has room for one byte, so exit(256) leaves 0. Every failure became a success. The fix unpacks it with WEXITSTATUS. On the F256, os9fork and wait pass OS-9's error code straight through, so the native driver never had this bug.

      The lost number hid a second bug. dcc -w means "check for errors and throw the output away". For it, the driver gave dcc68 an option -n, and dcc68 has never had one: it stopped with unknown flag: -n, and the driver called that success. The line came from CoCoC's older cc driver (Source/Compiler/CC/cc.c), which gave -n only to a one-pass compiler, c.comp, behind #ifndef TWOPASS. DCC's driver copied the line without the condition. Sending the output to /nil already throws it away, so the fix just drops -n. On the F256 that also needs a /nil device, which the boot disk lacked. The devsys disks now have it: boot/wildbits/l2 in devsys builds them from your NitrOS9 main tree, with pipes and /nil added (chapter 11). Now a good file gives 0 and a bad one 1, with or without -w.

      The lesson is about tests as much as code. A tool that always says "fine" can't fail a test, so a script checking only the exit code would have passed for years. Our harnesses compare the output files themselves, which is why they never relied on it.

      Step 14 went looking for more of these. las had one: its fatal errors exited with errno, the number of the last failed system call, which is 0 when nothing failed. "bad -D value" therefore meant success. It now exits 1 in that case. Four of CoCoC's library sources showed what that hid: on Linux they stop at a fatal error halfway through pass 2, leaving half an object file, and RMA has always called that success. dcpp looked like another case, exiting 0 when it ran out of memory, but that is deliberate: it writes the error into its output for dcc68 to report, and dcc68 does, then fails, and dcc stops. Checking it in MAME took one run. harness/silent.py keeps all of these checked, in two seconds.

      Pointers or a database

      Every link between dcc68's records is a raw pointer: a symbol points at its dimensions, its struct members, the outer symbol it hides, the next one in its hash chain. A pointer is an address in dcc68's own 64K, so every record has to live there. A database names its records by handle instead, a number the store turns into a location only when asked. las made that change in phase 8, which is how its symbols moved into banked blocks (chapter 9).

      How big would the change be for dcc68? Renaming the record fields in a copy of cj.h and compiling it answers that exactly, because every place that reads or writes a field becomes an error: 205 of them, 105 in declare.c. The count also turned up shortcuts that only work with real pointers. optim.c:444 copies the first six bytes of a symbol into a tree node, since both start with type, size and dimensions. optim.c:291 keeps a struct tag's symbol in the size field. lex.c:436 uses downptr to remember the hash chain a new entry hangs from. A handle API has to spell each of these out.

      The shape of the data is old. A symnode is a name with a set of named values, which Lisp calls a symbol with a property list. elem and dimnode are two-field cells, each holding a value and the next cell, which is Lisp's cons cell. So the API can be small in the same way: get a property of a handle, set one, make a cell, follow a cell. Two functions that take the field as a number cost less code than one accessor per field, and code is what dcc68 is short of.

      What big compilers do about headers

      By code, most of dcc68 is translation: parsing statements and generating 6809 instructions. By memory it is mostly remembering declarations, and most of those come from headers the file barely uses. GCC and Clang have the same problem at a larger scale: a C++ file often includes hundreds of thousands of lines of headers. Their answer is the precompiled header. The headers are parsed once and saved in a file with an on-disk hash table. Clang then loads a declaration from that file only when a lookup asks for its name (it calls this lazy deserialization). Unused declarations cost nothing, neither memory nor parse time.

      That is las's defs image (chapter 9) and dprune's idea joined into one design: the header database from the previous section, kept on disk and read on a lookup miss. For las/file_io.c it would leave about 7.8K of the 19.3K heap, because 11.5K is header declarations the file never uses. The catch is that a header holds two kinds of thing: macros, which dcpp needs, and declarations, which dcc68 needs. A precompiled header has to serve both programs, which is why Clang's format stores the preprocessor's state too.

      Measured: an image loader in dcc68

      A second branch (pch) tries it. A build of dcc68 with -DMKIMG compiles a file holding only #include lines and writes everything it declared to an image. Ordinary dcc68 takes -h=image: when lookup() makes a new symbol, pch.c checks a 256-byte filter in memory (one bit per name, so most new names cost no file access), then follows the image's hash chain on disk, and fills the symbol in as the header would have. Struct member lists load once per image, because dcc68 decides two struct types are the same by comparing their list pointers.

      The results, with dcpp's header text blanked: 55 of 55 devsys files compile to the same assembly as before. On the 6809 the loader adds 1,230 bytes, against banking's 3,314. Run on the OS-9 model, las/file_io.c, which ran out of memory before, compiles with 14,080 of its 16,384 bytes, and every file takes fewer instructions, because unused declarations are never parsed. It looked up 136 declarations with 618 seeks. Still 1,213 bytes too big to load on the F256, so the room question is the same one banking had, only a third the size.

      Messages in a file

      The room came from text dcc68 almost never prints. Its 92 error messages, from "; expected" to "argument type in \"newfunc\"", were 1,600 bytes of strings inside the program. OS-9 itself solved this long ago: printerr doesn't carry the text of ERROR #216, it reads it from /dd/SYS/errmsg. dcc68 now does the same. Each message in the source is a 2-byte code with the high bit set, named in msgs.h (M_MULTIPLE_DEFINITION), and msg() reads that line of /dd/SYS/dcc68.msg only when an error is actually reported. The texts stay in msgs.h as comments and the makefile generates the file from them, so there is one place to edit.

      Two details matter. msg() reads the file a byte at a time with open and read, not stdio, because one of the messages is "out of memory", and stdio needs memory for its buffer. And if the file is missing it prints "message 44" instead of nothing. The output is unchanged: all 313 test inputs give the same messages as before, including the 46 CoCoC files that fail. With that and a trimmed loader, dcc68 is 48,341 bytes, 43 under the six-block limit, and las/file_io.c compiles on the model in 14,336 of its 16,384 bytes.

      When is an image the right one?

      An image stands for the headers as they expanded when it was made. Two things can make that false. A header can be edited afterwards. Or the file can expand it differently: las's rma_main.c says #define MAIN before #include "rma.h", which turns every extern in it into a definition. With an image made without MAIN, dcc68 would compile it wrong and say nothing.

      So dcpp checks. With -h=image it still reads every header, because their #defines matter, but passes none of their text on, and it computes a checksum of each header's text as it goes. The image holds the same checksum, made by the writer from the text it read. A header that differs stops dcpp with exit status 2, and dcc then compiles that file the ordinary way and says so: dcc: 'rma_main.c' compiled without las.img. An image can make a compile smaller and faster, never wrong.

      The check had to be exact, and that has a cost. Headers share guards: CoCoC's stdio.h and stdlib.h both declare size_t, and only the one included first does. So stdio.h's text depends on what came before it. A looser check, such as "every line the file got is somewhere in the image", would accept that, but it would also accept an #ifdef inside a struct that left out a member, and then the struct's layout would quietly differ. That is why other compilers tie a precompiled header to an exact prefix of includes. For las one image fits 15 of its 17 files; labels.c includes stdlib.h first and falls back. All 17 objects are byte-identical to the ordinary build's.

      The image writer, dcc68w, is a separate program built from dcc68's own source. It only reads declarations, so it leaves out the code generator, statements and initialisers. That makes it four blocks of code instead of six, with 32K for data where dcc68 has 16K. It needs that room: parsing all of las's headers takes 27,136 bytes. On the model the whole chain runs natively, and las/file_io.c, which dcc68 couldn't compile before, compiles with the image to the same assembly as on Linux.

      Fitting las to its image

      Building all of las on the emulated F256 found two files the image didn't fit, and both taught something about headers. rma.h starts by redefining two words for DCC, which has neither: #define void int and #define const. Every header read after it is read with those definitions, so stdlib.h after rma.h is different text from stdlib.h before it. rma_main.c and labels.c included stdlib.h first, and their checksums didn't match. Moving rma.h to the top gives byte-identical objects, so they now do it the way the image does. That is the rule every precompiled-header system ends up with: the project header comes first.

      Step 20: te, and the database after all

Symbols and list cells live in RAM blocks reached by handle, and a file's names no longer have to fit in dcc68's own 64K. Its problem had been size: 3,314 bytes too big. The room came from looking at what each call costs on the 6809.

      sget(s, S_SIZE)   ldd #1 / pshs d / ldd 6,s / pshs d / lbsr sget / leas 4,s   12 bytes
SG_SIZE(s)        ldd 4,s / std <symh / lbsr sg1                            7 bytes

      Each field got its own entry point in assembly (sg0 for the type, sg1 for the size…), so a call no longer pushes the field number. The handle goes in a direct-page variable, symh, instead of on the stack, so there's nothing to pop afterwards. The entry points share one routine through an old 6809 trick: fcb $8C is the opcode of cmpx #, which swallows the next two bytes. So sg9: ldb #18, then $8C, then sg8: ldb #16… falls through, skipping every later ldb, to the common code. Where a function uses several fields of one symbol it maps the record once, p = SYMP(s), and then writes p->type. That pointer is good only until the next access to any other symbol, las's phase 8 rule. A Linux build that copies the one window in and out catches any pointer kept too long.

Its 16-bit handles held the block in 5 bits and the offset in 4-byte units in the other 11, which reaches 31 blocks (248K). Counting in 8-byte units moves one bit across: 6 bits of block and 10 of offset, 62 blocks, 496K. te uses 45. The F256 has about 230 free blocks, so the RAM was always there; only the number format was too small.

      Step 21: dev-cc, and a bug that hid in a pattern file

      Next was dev-cc, the version of te you're still working on: 5,257 lines, a quarter bigger. It found two more limits, and on the way a compiler bug older than devsys.

      dco68's records. dev's assembly is 15,070 lines, and dco68 needed 71 of its 62 blocks. Counting what fills them showed a layout problem, not a lack of RAM. Half the memory was instruction records, and each carried an 11-byte field for its mnemonic, though a file uses only about 100 different mnemonics. Every operand got a 16-byte slot, though most are a few characters (4,s, #12). Every label had room for 33 characters, though most are like _123. Now each distinct mnemonic is stored once, in ordinary memory, and an instruction holds its number. Operand and label texts take what they need, in 8-byte steps. te went from 45 blocks to 28 and dev fits in 42, which also means fewer block switches. Room for the new code came from writing the small helpers in assembly. dco68 is now 14 bytes under its limit.

      The same measurement turned up a latent bug. When a pattern rewrote an operand, dco68 copied the new text into the old slot, and a longer operand in a 16-byte slot ran into the next record. No input had done it yet; operands that grow now get a new record.

      llink's buffer. llink reads each psect whole, patches its references and writes it out. dev is one 31,826-byte psect, more than llink's memory holds beside its tables. Now the psect lives in up to eight RAM blocks behind a window, like everything else in devsys that outgrew 64K.

      The bug. The first run of the new llink allocated one block where it needed four. Its loop was while (n > 0) with an unsigned n, and the code that reached the 6809 was:

      _2   ldd   4,s          D = n
     bhi   _3           loop while n > 0 ... or so it seems

      dcc68 had written cmpd #0 between the two. A rule in dco68's pattern file, unchanged from CoCoC, removes it: a load sets the Z and N flags just as the compare would. But bhi, "branch if higher", tests the carry flag as well, and the compare clears carry while a load leaves it alone. So the loop asked a question about a carry left by n - 8192 a few instructions before. The rule now removes the compare only before a branch that tests Z, N or V (beq, bne, the signed comparisons, bpl, bmi).

      Was anything else miscompiled? Comparing the old rule's output with the new one's on every C file we have answers it: 10 places, all in llink. Two were in llink's existing code, unsigned tests that had worked because the carry happened to be clear. Every other tool came out byte for byte the same. A new test, harness/native/unsgn.c, counts blocks the way llink does; with the old rule it says 1, not 4. It's the second time a CoCoC rule gave wrong code without a word (the first was dcc68's register tracking, D53), so it now runs in silent.py and in the native cc suite.

      In MAME, dcc dev.c -m=2k then built dev in 124 seconds, identical to the Linux build. Then you ran it on the K2 (card 7): the dev it wrote to /dd/DEVSYS is byte for byte the Linux build, 35,948 bytes, and /dd/TMP was empty afterwards, so dcc removed its intermediate files. The card's file times (/dd/TMP changed at 07:20, dev written at 07:22) put the build at about two minutes, as in MAME. A 5,257-line C program now compiles on the machine it runs on.

      Step 22: room to change

      After te and dev, three tools were nearly full: dco68 had 14 bytes left under its limit, dcc68 114, and las 53 bytes of data. At those margins, the next bug fix might not fit. So step 22 made room before anything else. How the room was found shows how the limits really work.

      dco68 into three blocks. dco68's 15,616-byte limit isn't about RAM. It's the top-slot rule from chapter 11: a program that maps windows must have its own code in the top slot ($E000), or F$MapBlk hands out that slot and covers the system page. Two blocks hold at most 15,616 bytes ending by $FD00; three hold 16,385 to 23,808. So dco68 got bigger on purpose: dcc/COpt/topslot.c ends in 2,048 zero bytes (rzb 2048), which take it to 17,692 bytes, mapped from $A000, with its code ending at $E2DC. It now has about 6K to grow. When it needs more, zeros come out.

      The zeros first went in a file of their own, and llink quietly left them out. llink, like Microware's rlink, keeps an object only if something uses one of its names, even when it's named on the command line (adj_ofst in llink/rl_02.c counts a module only when one of its symbols is referenced). A file of nothing but zeros has no names. The fix was to put the zeros next to the code that depends on them: dco68's start-up check that its code reaches $E000 moved into topslot.c as topslot(), and bank.c calls it, so the zeros come along. A new script, harness/topslot.py, checks the same rule for every tool that maps windows (las, llink, dcc68, dco68) each time native/GNUmakefile links one, so a size change is caught on Linux instead of hanging the F256.

      The 64K is a budget of eight slots. A third module block costs one slot of dco68's address space. The model showed what fills the rest: dco68's data needs about 10.5K, two slots, of which about 3.5K is the optimizer's patterns read at start. So it's 3 module slots + 2 data slots + 3 windows = 8, one window fewer than before. Two changes went with it. The patterns' mnemonics are now kept once in dco68's table of mnemonics (D58), not copied for every pattern, which saves 768 bytes. And three windows instead of four cost about 10% more window changes: te 25,440 → 27,929, dev 51,752 → 55,846. At about 288 µs per change on the F256, that's under a second on te.

      A whole library module for one call. dcc68 can't take a seventh block: its module, one data slot and its window already fill all eight. So its room had to come from smaller code. The map showed 400 bytes of fseek_a from the C library, linked because dcc68 calls rewind once, to read back its strings file. A library is linked a member at a time, and rewind lives in the same member as fseek and ftell. Closing the file and opening it again does the same job with fopen, which dcc68 already uses. CoCoC had once done exactly that; the old code was still there, commented out. dcc68 went from 114 bytes spare to 471.

      That same code had a small bug, open since step 17: when a fatal error ended a compile, dcc68 left its empty cstr.XXXXXX strings file in your directory, because errexit() didn't remove it. Both exits now call rmstrings(), and silent.py check 7 makes sure. Writing that check showed something about the model too: os9run.py didn't implement I$DeletX, the call the C library's unlink uses, so in the model the strings file was never removed, not even after a good compile. It does now.

      las: a budget, not a byte count. "53 bytes of data left" is only part of the picture. las's data block holds its static variables plus las_MEM, a pool for the stack, the stdio buffers and getmem, and at the worst input seen that pool still has 869 bytes free. The real room is the two together. The biggest static item is 1,130 bytes of opcode and directive tables: each entry is a pointer to a name, plus an opcode and flags. Code can't hold pointers, because a module isn't relocated. Stored as offsets, the tables could move into the code and free about 1.1K of data. That's recorded as an option, not done in this step.

      Building the C library ourselves

      Until step 18 every devsys C program linked against CoCoC's clib.l, sys.l and cstart.r: binaries made in 2022 by tools that kept 8 characters of a name. Now clib/ holds their sources (our fork of CoCoC's KLibc and SysLib), and clib/GNUmakefile builds them with our own dcc68, dco68 and las. A library is just its members' object files written one after another, in a fixed order. Order matters because llink reads a library once, front to back, and takes a member only if it defines something still missing. So a member has to come before the members it calls.

      How do you know a rebuilt library is right? Compare it with the one it replaces. harness/libdiff.py takes two libraries apart into members and compares each one's code, data, definitions, references and fixups. With --names8 it first cuts every name to 8 characters on both sides, so a member that differs only by longer names counts as the same. Of the 134 members of clib.l, 126 came out identical, and each of the other 8 had a reason we could point to. Some sources changed in CoCoC after 2022, when the time functions were rewritten in C. CoCoC's compiler changed too: one char increment became addd #1 where it had been addb #1, one byte longer, and CoCoC's own current compiler makes the same code. One difference was our own D43 fix. The comparison also found real problems:

      • A divide that didn't link. dcc68 turns unsigned long division into a call to _ludiv, which CoCoC added to its sources in 2023 but never to its clib.l. Any program dividing unsigned longs failed with "unresolved references".
      • 300 names too many. devtyp.a and sleep.a read os9defs.a inside their psect, so all its F$Link:-style labels (a colon makes a name global) were exported from both. A program using isatty and sleep stopped with "name clash". Every other member reads the defs before its psect, so these two now do too.
      • Names the header promises. sets.h declares sintersect, but sets.a only had the label sinterse. Only D19's alias had made that work.
      • Start-up code. cstart.r, the code that runs before main, came from Microware. It had two bugs that Kreider's version in KLibc fixes. When a program has direct-page data but no other initialised data, a branch skips the clra, so the program's zeroed variables (the BSS) get filled with the last byte copied. And the stack check misses a request so big that it wraps below address 0. We took Kreider's code but kept Microware's stack figure (896 bytes): Kreider's 1,280 would have pushed las's data past its one 8K block (chapter 11).

      The five members with no source (scanf, qsort and three others, Microware's own objects) go in as they are. They are ROF version 0, but none defines an 8-character name, so no alias can ever be needed for them.

      Floating-point constants: the same bytes on both machines

      A double on the 6809 is 8 bytes. The last byte is the exponent, stored with 128 added (a bias, so it never needs a sign). The first 7 bytes are the mantissa, the binary digits of a fraction between 0.5 and 1. Such a fraction always starts with a 1 bit, so that bit isn't stored (the hidden bit), and its place holds the sign. The value is 0.1mmm… in binary times 2exponent−128, and an exponent byte of 0 means zero. Here is what dcc68 writes for a few constants (docs/learn/examples/consts.c):

      double one   = 1.0;      fdb 0,0,0,129       0.1b x 2^1
double half  = 0.5;      fdb 0,0,0,128       0.1b x 2^0
double ten   = 10.0;     fdb 8192,0,0,132    0.101b x 2^4 ($2000: 0.1 hidden, then 01)
double minus = -2.5;     fdb -24576,0,0,130  sign bit set ($A000)

      A compiler has to turn the text 0.3333333333333333 into those bytes. dcc68 on the F256 does it with the 6809's own arithmetic from the C library (cfloats.a). It adds up the digits as a 56-bit integer, then divides by a power of 5 and moves the exponent by the matching power of 2 (10n = 5n × 2n). On Linux it used the PC's doubles (IEEE 754) and converted the result. Those have 53 bits of mantissa, not 56, so the same line gave different bytes:

                                CoCoC's Linux dcc68          devsys (= the F256)
0.3333333333333333        fdb 10922,-21846,-21846,-22401   ...,-22913
1.7014118346046923e+38    fdb 0,0,0,0                      fdb 32767,-1,-1,-1

      The second line is HUGE_VAL, the largest double. In IEEE it rounds to exactly 2127, one step past the 6809's largest value. The converter's exponent wrapped around, and the Linux compiler wrote 0 with only a warning. A library built on Linux would have returned 0 from ldexp where it means "too big". That's why this mattered for step 18: CoCoC built its library on the 6809, and we build ours on Linux.

      The fix gives the Linux dcc68 the 6809's arithmetic. It keeps every constant in the 6809's 8 bytes, and does each step the way cfloats.a does: multiply by shift-and-add, divide by long division, round on the one bit below the result (half up, ignoring the rest), and stop with the same error when an exponent overflows (dcc/CC09/fp6809.c). Copying the rounding exactly was the point. A "more correct" Linux result would still differ from the F256's.

      Testing by comparing machines. harness/fltcheck.py writes thousands of generated declarations, compiles them with dcc68 on Linux and with native dcc68 on the 6809 model, and compares every byte. The first big run found what reasoning had missed. Near 256, the digit sum is assembled as high part × 232 + low part, and the 6809's add rounds a bit away there. So the Linux side now does that add the 6809 way too. The comparison also found bugs in the native compiler that Linux had hidden, because IEEE got these cases right:

      • 0.0 was 2126. Dividing zero by 5 gives zero, and then the exponent was moved anyway. Since the 6809 format means zero only when the exponent byte is 0, the result was a huge number.
      • 4294967295.0 was 3,865,470,565. The digit sum's low 32 bits were added as a signed long, so when their top bit was set they counted 232 less.
      • 65535 was the int −1. K&R C says a decimal constant too big for an int is a long, and the Linux build did that. The 6809 build only checked that the top 16 bits were zero. Only MAME caught this one, building harness/native/clibtest.c.

      dcc68 has to fit in 48,384 bytes, so each fix was written for size: the carry for the low word is added a byte at a time (25 bytes). The rest of the Linux work costs the 6809 nothing, because fp6809.c is only in the Linux build. dcc68 now has 3 bytes to spare.

      The 65535 fix turned up one more bug, in dcc68's code generator. dcc68 remembers what each register holds, so it can skip loading a value that is already there. That memory compares the expression but not its size. After ldb 12,s, which loads one byte, it believed D held the two bytes at 12,s, and it left out the ldd 12,s that was needed. The first version of the fix compiled to wrong code because of this. Writing the test differently avoided it then. The next section fixes the comparison itself.

      Remembering what a register holds

      A compiler that reloads every value it uses writes slow code. So dcc68 keeps a note of what D and X hold (dregcont and xregcont in regscont.c, compiled in with -DREGCONTS). The note is a copy of the expression tree that was last loaded. Before loading an expression, dcc68 compares its tree with the note. If they match, the value is already there, and dcc68 uses the register instead. Anything that changes a register or the memory a note refers to has to clear or update the note. This is called register tracking, and every compiler has some form of it.

      The comparison is cmptrees(). It walked both trees and checked three things at each node: the operator, the value (an offset or a symbol) and the modifier. It didn't check the type. Usually that doesn't matter, since the same place in memory normally has the same type. A union is the exception: it puts different types at one address. Here is docs/learn/examples/regreuse.c:

      union u { char c[2]; int i; };

int both(p)
union u *p;
{
    char c;
    int i;

    c = p->c[0];
    i = p->i;
    return c + i;
}

      p->c[0] and p->i are the same tree apart from the type: "the thing at p, offset 0". CoCoC's dcc68 compiles it like this:

       ldb [7,s]      c = p->c[0]: one byte into B
 stb 2,s
 std 0,s        i = p->i: stores D, which is not p->i

      After ldb, only B holds anything useful. A holds whatever an earlier instruction left there. dcc68's note said "D holds the thing at p", and the note matched p->i, so it stored D without loading it. The other order goes wrong too, because the 6809 is big-endian: it stores the high byte of a word first. After ldd [7,s] loads p->i, B holds the byte at offset 1, but p->c[0] is the byte at offset 0. The fixed dcc68 adds the missing line: ldd [7,s] before std 0,s.

      The fix: compare widths, but only at the top

      The obvious fix is to compare the type at every node. We measured it on Linux before writing it: it changed 34 of our own files, and every change we looked at made the code worse and fixed nothing. The cause was X. X usually holds a pointer, and the same pointer can appear in a tree as a char * in one place and an int * in another. Both are the same two bytes in X. Comparing types at every node made dcc68 reload pointers it already had.

      So the check goes where the problem is: at the top of the tree, which is the value sitting in the register. There the question is only whether it is one byte (a char, in B) or two (in D or X). Lower in the tree a char used as an int already has its own conversion node, so it can't be confused. The new cmptrees() is the old comparison, renamed sametree(), plus that one test.

      One caller had to keep the old comparison. When dcc68 stores into memory, subtree() looks for the stored place inside each note, to forget a register whose value just changed. That search must ignore widths. If D holds the int p->i and a char is stored at p->c[0], half of that int has changed, and the note has to go. So subtree() still calls sametree().

      Was anything compiled wrong?

      A bug like this raises the question of what it has already broken. We found out by measuring instead of guessing. A scratch build of dcc68 kept the old behaviour but printed a line every time a match joined two different widths. It compiled 346 C files: every devsys tool, the C library, all of CoCoC's sources and the test programs. It printed one line, at a label in llink (rl_03.c:574), where the code that follows reloads the value anyway. So nothing we had built was wrong. The fixed dcc68 gives the same assembly as before on all 346 files, so the only code that changes is code that was wrong.

      harness/native/regwidth.c keeps it fixed. It reads one place as a char and as an int, in both orders, and checks the results. CoCoC's dcc68 gets two of its four functions wrong. silent.py builds and runs it on the OS-9 model, and native.py cc compiles and runs it on the emulated F256.

      Finding 85 bytes

      The check costs 85 bytes of 6809 code, and dcc68 had 3 to spare. We looked for code that was long for no reason, so that no feature had to go. lexinit() in lex.c puts C's keywords into the symbol table when dcc68 starts. It did that with 36 calls in a row, install("double",DOUBLE), install("float",FLOAT) and so on, and each call is about 13 bytes of code: push two arguments, call, pop them. Now the names are one string, the types are one 36-byte table, and a loop makes the calls:

      p = "double\0float\0typedef\0static\0sizeof\0int\0" ...;
for (i = 0; i < sizeof kwtypes; ++i) {
    mosflg = (i >= KWMOS && i < KWMOS + 7);
    install(p,kwtypes[i]);
    while (*p++) ;
}

      The order is the same as before, so the symbol table comes out the same. The names are a string literal, which DCC puts in the code. A static array would have put them in dcc68's data, which is limited to 16K and holds the symbol table. Only the 36 type bytes went into data. This saved 477 bytes, so with the fix in, dcc68 is 47,990 bytes, with 394 to spare.

      CHAPTER 08Level 2 memory

      The 6809 has 16-bit addresses, so it can see 64K at once. The F256 has much more RAM than that. Level 2 bridges the gap with the MMU (memory management unit): the 64K a program sees is split into eight 8K slots, and the MMU decides which physical 8K block of RAM appears in each slot. You can see the slots in defs/wildbits.d: MMU_SLOT_0 to MMU_SLOT_7.

      Each process gets its own set of eight slots, so each process sees its own private 64K. A process might look like this (illustrative):

      $E000
      program module (code)
      $C000
      program module (code)
      $A000
      unused
      $8000
      window: extra RAM mapped in on request
      $6000
      unused
      $4000
      data area (tables grow here)
      $2000
      data area
      $0000
      data area + stack

      The limit that matters: code, data and stack all have to fit in that one 64K. Level 2 gives each process its own 64K, but not more than 64K.

      The way around it: a process can ask for extra RAM blocks (F$AllRAM) and map one into a free slot when needed (F$MapBlk), then swap it for another. This is bank switching. gfxstatus.as does exactly this to reach the graphics hardware: it maps block $C1 in, reads the colour table, and unmaps it.

      Chapter 4's symbol table holds every name the assembler has seen. For NitrOS9 that's mostly the defs files. I measured real F256 sources:

      Why long names hurt

      The old Microware tools kept only the first 8 characters of a name. That made every entry small, but MMU_SLOT_0 through MMU_SLOT_7 would all become the same name, MMU_SLOT. The F256 defs have 167 such collisions, so long names are a must.

      The C version of RMA allows 63 characters, but stores every name in a fixed 64-byte box. With 12 bytes of other fields, that's 76 bytes per symbol on the 6809. For fm.asm: 2,353 × 76 ≈ 179K. The process has about 25–30K to spare.

      $10used before it was defined. Still set at the end means never defined, so it's externalprintf

      s_ofst is the value: an offset within its section for a label (helper is at code offset $000D, and total sits at data offset $0040, just after the 64-byte buffer), or the number itself for equ and set.

      reftbl points to a list of small records, one for each place the name is used. For printf it says “used at code offset $000A”. At the end, that list becomes the object file's “names this file needs” section, the red part of chapter 5's hex dump.

      Making the record fit the name

      The average name in the defs is 8 characters, yet every record reserved 64 bytes for it. Roadmap phase 2 made each record exactly as long as its name needs, using a standard C trick. The name becomes the last field and is declared as a one-character array:

      struct symblstr
{
    ...                         /* the same 12 bytes of fields */
    char symblnam[1];           /* the name: must stay last    */
};

      When sym_add creates a symbol, it asks for the record's size plus the name's length: sizeof (struct symblstr) + strlen (name). The [1] already covers the zero byte that ends the name, so the name's other characters run on past the end of the declared array, into memory that was requested for exactly that purpose. C doesn't check array bounds, which is what makes the trick possible, and also what makes it easy to get wrong.

      A record now takes 12 bytes plus the name plus 1. Measured on real files:

      FilesBeforeAfter
      376 RMA and DCC-compiled files, the C toolchain's own inputslargest 40.4Klargest 10.7K
      265 NitrOS9 Level 2 files, with the full defsmedian 109Kmedian 30.6K

      The table is about 3.5 times smaller. The C toolchain's files now fit in the 25–30K a 6809 process has to spare, but NitrOS9 files still don't: the defs alone are about 1,500 names. That's the job of the banked blocks and precompiled defs.

      Checking for memory mistakes

      Get the size calculation wrong by a few bytes, and each name overwrites the start of whatever was allocated next. The output might still look right, until it doesn't. The regression test can't reliably see that. A special build can: AddressSanitizer, a compiler option that surrounds every allocation with guard zones and stops the program the moment anything touches one. All 740 regression inputs ran clean under it.

      Then the negative control from chapter 10: deliberately allocating names too short. It needed 4 bytes too short, not 1, before the sanitizer complained. The reason is padding. On Linux the compiler rounds the record up to a multiple of 4 bytes so its fields line up efficiently, and those spare bytes quietly absorb a small mistake. The 6809 has no such rule, so there a 1-byte mistake would corrupt memory, and only on the F256. Knowing where your safety net has holes is part of using it.

      Memory that's never been set. The same tool caught a bug that had been in rlink all along. Its allocator handed out memory without clearing it, and some of rlink's code assumed new records started at zero. Under the sanitizer, which deliberately fills new memory with a recognisable pattern (0xBE), every link crashed. In a normal build, fresh memory from the system usually happens to be zero, so rlink had been working by luck. Clearing each allocation fixed it. Bugs like this are the worst kind: invisible until something about the memory changes, such as moving to a different machine.

      Finding a name quickly: hashing

      The assembler looks names up constantly. Every label is added in pass 1 and found again in pass 2. Every operand that names a symbol (os9 F$Exit, lda #MMU_SLOT_0, lbsr print) is a lookup. That's thousands of lookups per file, so the cost of one lookup is multiplied thousands of times.

      Here are three ways to find one of the 1,664 names in the Level 2 F256 defs, measured on those real names:

      MethodAverage comparisonsWorst case
      Check every name in turn8321,664
      One sorted tree of all names20.753
      64 buckets, a small tree in each (RMA, las)5.114

      Step 1: pick a bucket

      A hash function turns a name into a number, always the same number for the same name. RMA's is about as simple as one can be: add up the character codes, then keep the lowest 6 bits. Six bits hold 0 to 63, so that's the bucket number.

      For F$Exit: F (70) + $ (36) + E (69) + x (120) + i (105) + t (116) = 516. 516 is 8 × 64 + 4, so the low 6 bits are 4, and F$Exit lives in bucket 4. Try any name:

      Why 64, a power of two? Keeping the low 6 bits is the same as taking the remainder after dividing by 64, but it's a single ANDB #$3F instruction. The 6809 has no divide instruction, so a bucket count like 50 would need a slow division routine for every lookup. And 64 bucket pointers take only 128 bytes.

      Once the bucket is known, the search only looks there. Every other name is ruled out without a single comparison.

      Every bucket gets used. The emptiest holds 15 names and the fullest 41, around an average of 26. That evenness is what makes hashing pay off: each lookup searches about 26 names instead of 1,664.

      Adding characters ignores their order, so different names can have the same total. In the defs, 1,337 names share their total with at least one other name. For example, F$Link, SS.DRAM, E$Sect and WIZ_MR all add up to 504, so all four share bucket 56. Two names in one bucket is called a collision. It's normal, and the tree in each bucket sorts it out. On the other hand, names that differ in one character land near each other but not together: MMU_SLOT_0 goes to bucket 31, MMU_SLOT_1 to 32, and so on up to MMU_SLOT_7 in 38.

      A stronger hash (CRC) spreads names a little more evenly, but on these names it still averages 5.1 comparisons, improving only the worst case, from 14 to 12. The cheap hash is good enough because the trees absorb the unevenness.

      Step 2: search the bucket's tree

      Each bucket is a binary search tree: every name has up to two branches, with names that sort earlier on the left and later on the right. Here is bucket 25, the emptiest, built from its 15 names in the order the defs files define them: D.SWPage, D.BTHI, M$IDSize, P$SWI2, P$DeadLk, FMWRIT, V$DESC, E$NoVRef, PD.T0S, PD.DCP, PE.FilNm, FDSL.B, ROMBlock, T1_CTRL, VS_HDAT0.

      Finding PE.FilNm takes 6 comparisons, shown as steps 1 to 6: D.SWPage → M$IDSize → P$SWI2 → V$DESC → PD.T0S → PE.FilNm. Each comparison rules out a whole branch.

      “Sorts earlier” means comparing character codes, as C's strcmp does. In those codes $ (36) comes before . (46), digits come before capital letters, and capitals before lower case. That's why P$SWI2 sorts before PD.T0S.

      The tree's shape depends on the order names arrive. D.SWPage came first, so it's the root. When names arrive already in alphabetical order, each one goes to the right of the last, and the tree becomes a long chain. That's the reason for the occasional worst case of 14 comparisons.

      The algorithm

      Finding a name, as sym_find in las/symtab.c does it:

      1. Add up the name's character codes and keep the low 6 bits. That's the bucket.
      2. Start at the bucket's first node. If the bucket is empty, the name isn't defined.
      3. Compare the name with this node's name.
      4. If they're equal, this is the symbol. If the name sorts earlier, move to the left branch; if later, to the right branch.
      5. If there's no branch that way, the name isn't defined. This spot is also exactly where sym_add attaches a new name.
      static struct symblstr **
bucket (char *name)
{
    register char *p = name;
    int sum = 0;

    do
    {
        sum += *p;
    } while (*(++p) != '\0');

    return &Buckets[sum & (NBUCKETS - 1)];
}

      The tree has one more trick. To print the symbol table and write the object file, the assembler visits every name in order. Normally that needs a stack to remember the way back up the tree, and stack space is precious on a 6809. RMA avoids it with a threaded tree: when a node has no right branch, its unused right pointer points instead to the next node in order. One flag bit, LOC1BYT, says which kind of pointer it is. Walking the whole table is then just following pointers.

      The three-part fix

      PartIdeaEffect
      Compact entriesStore each name at its real length instead of in a 64-byte box.About 18 bytes per symbol instead of 73. No slower.
      Banked tablesKeep the table in extra RAM blocks, mapped in one at a time (chapter 8). Done in phase 8, below.The table is no longer limited by the 64K space.
      Precompiled defsRecord once what reading the defs did, in a file. Later builds create those symbols straight from the file instead of re-reading 1,600 definitions in each pass. Done in phase 9, below.A small module assembles in a sixth of the work.

      Precompiled headers in modern C compilers use the same trick: do the expensive, unchanging work once and save the result.

      Hiding the table behind an interface

      All three parts change how the table is stored. If code all over the assembler walked the trees itself, each change would mean editing every one of those places, and missing one would break something quietly. So the first step, roadmap phase 1, changed nothing visible. It moved all the code that knows how symbols are stored into one file, las/symtab.c, behind three functions:

      FunctionWhat the rest of the assembler gets
      sym_find(name)The symbol, or nothing if it isn't defined.
      sym_add(name)A new, empty symbol.
      sym_walk(fn)Calls fn once for every symbol, in table order. Used to print the symbol table and to write the object file's name lists.

      That's an interface: a promise about what you can ask for, with the how kept private. Before, the hashing and tree code was spread over labels.c and file_io.c. Now the hashing, the buckets and the tree are invisible outside symtab.c, so compact entries and banked blocks can replace them without touching the callers.

      One detail had to be preserved exactly: the order sym_walk visits symbols in. It decides the order of names in the listing and in the object file, so changing it would change the output, even though no symbol changed.

      Moving the table into banked blocks

      Phase 1 hid how symbols are found. But once found, a symbol was still a pointer, and about 130 places in the assembler read its fields through it. That's fine while the table sits in ordinary memory. In a banked block it isn't. Only one block is visible at a time, in an 8K window, and a pointer into the window is only good until another block is mapped there. After that the same address shows a different block's bytes.

      Step 1: handles instead of pointers

      So callers now get a handle: a number that names a symbol without being its address. Only symtab.c turns a handle into a pointer, and it uses that pointer at once. Everyone else asks: sym_typ(h), sym_setval(h, v), sym_name(h). To make sure nothing was missed, the symbol's structure was moved inside symtab.c, where no other file can see it. Every old access became a compile error, about 150 of them, and each was rewritten. The output didn't change: the regression test stayed at 741 of 741.

      A handle is 16 bits. The top 4 hold the block number plus one, and the low 12 hold the offset in the block divided by 2 (entries start on even addresses). Block 2, offset $1A4 is handle $30D2. That allows 15 blocks, 120K of symbols. The largest file in the build needs 51K. Adding one means no handle is ever 0, so 0 can still mean "no symbol".

      Step 2: the window

      The blocks come from F$AllRAM. F$MapBlk maps one into the highest free slot of the process, which for las is the slot just below its module, and F$ClrBlk unmaps it again. las now looks like this on the F256:

      $6000
      las module, five slots up to $FFFF
      $4000
      window: one symbol block at a time
      $2000
      unused
      $0000
      data and stack: 8K

      There's one trap, and it's subtle. This line copies one symbol's field into another's:

      SP (new)->right = SP (parent)->right;

      SP() maps a symbol's block and returns a pointer into the window. If the two symbols live in different blocks, working out the right-hand side maps the parent's block, and the pointer for new now points into the parent's block. C doesn't even say which side is worked out first. The fix is a rule: no statement in symtab.c touches two symbols. The value goes through a local variable first.

      Testing for a bug Linux can't have

      On Linux every block stays in memory, so that bug can't show up there. A special test build, las/build/bankwin, fakes the window: it has one 8K buffer and copies a block in and out whenever another is needed. A stale pointer then reads the wrong block, exactly as on the F256, and the regression test sees wrong output. To prove the test can catch it, I put the line above back. The normal build still passed 741 of 741. The window build failed 242 of 741. With the line fixed, it passes again.

      A block from F$AllRAM also stays allocated after a program ends unless the program gives it back with F$DelRAM. So every way out of las returns its blocks, and the host model (chapter 11) reports any block left behind.

      The result

      On the emulated F256, las now assembles scfg.asm byte for byte as the Linux build does. It uses 6 blocks of symbols, switches the window about 22,500 times, and needs only 8K of ordinary data, where 41K wouldn't fit before. It is slow, though. A big NitrOS9 file takes minutes, because every pass reads 230K of defs and each switch costs two system calls. Phase 9's precompiled defs go after that.

      Measure before you build. The plan was to bank rlink the same way, because it ran out of memory linking las. Counting where its memory went showed something else: 14K of its 20K of static data was one table, used only with --lwlink, that I had added in phase 3b as a fixed array. Allocating it only when needed let rlink link every tool with room to spare. No banking needed.

      Saving the defs: precompiled images

      Almost every NitrOS9 module source starts the same way:

                          ifp1
                    use       defsfile
                    endc

      defsfile pulls in os9.d, scf.d, rbf.d and wildbits.d: about 2,000 lines of equ, set and rmb. In lwasm mode ifp1 is true in both passes (chapter 4), so the assembler reads all of it twice. On the F256 we measured level1/cmds/echo.asm, a 34-byte module, in the host model (chapter 11): 33.7 million 6809 instructions, and 99% of them were the defs. The defs are the same for every file in a build, so that is the same work done over and over.

      The idea

      Do the work once and keep the result. The first time las --defsimg=FILE reaches use defsfile, it reads the defs as usual and records what they did into FILE, a defs image. Later runs find the image and create the symbols straight from it. Compilers do the same with precompiled headers. harness/imgdump.py prints an image. This is the one native las wrote on the emulated F256:

      IMG: complete, version 2, options 0x07, for 'use defsfile'
  defined before:  NOS9MAJ      typ 05 msk 82 value 0x0
  defined before:  jr2          typ 05 msk 82 value 0x1
  ...
  file  os9.d        /dd/S/os9.d  stamp 7e0a021218000111c2
  nam   'os9.d'
  ...
  counter 0x0 -> 0x8; blocks +260 (local=new); lines +3080; globals +0; if count +4
  25 conditionals: 1011110111001101100111110
  pass 2  OS9.D                typ 05 msk 82 value 0x1
  records: E 1, F 5, G 1, P 5, S 1639, T 11, Z 4

      Most of the 27,433 bytes are the 1,639 symbols (S). The rest is everything else reading the defs changes. That turned out to be more than symbols:

      • the location counter: the defs' top-level rmb lines leave * at 8, exactly as lwasm does;
      • the 25 conditionals' results, which pass 2 replays (chapter 4);
      • the blank-line count that numbers local-label blocks, and the line count used in messages;
      • RMA's if count. It goes up at every if but not down at the endc of a false one, so the defs raise it by 4. The image must too, or a stray endc later would be reported differently;
      • nam and ttl. In pass 1 they set the title only if it is still empty, in pass 2 always. So the image keeps the lines themselves (T) and does them again with the same rule;
      • a few symbols pass 2 changes when it reads the defs again (Z), such as the include guard OS9.D.

      Each of these was found by testing, not by planning: the first version differed until it was right. The symbols aren't saved as raw table blocks, either. Each bucket's tree depends on what was in the table before the use, so loading adds them again in the order they were first created. The trees then have the same shape as after reading, and lookups cost the same.

      When is the image still right?

      This is cache invalidation: knowing when a saved result no longer matches what doing the work would give. Using a stale image is the worst possible failure, because the module comes out wrong with no error. The F256 defs show why: os9.d says IFNE H6309, so assembling with -DH6309=1 defines different symbols. Loading an image made without it would quietly build a 6809 module with the wrong definitions.

      The rule las uses is deliberately blunt. It loads the image only when reading the defs would certainly do the same:

      • the symbols defined before the use are exactly those at recording: the same names, types and values (P). Usually these are the -D symbols. So whatever the defs look at is as it was, and nothing they create exists yet;
      • every use resolves to the same path, and that file has the same date and size (F). On the F256 the date comes from the file's descriptor (I$GetStt, SS.FD), as make would use it;
      • the same options and location counter.

      If anything differs, las just reads the defs. If a file changed, it also records a new image. A first version tracked each name the defs looked up, which is more precise. But RMA already creates a table entry for any name used before it is defined (H6309 in IFNE H6309), so those names show up as created symbols anyway, and the blunt rule covers them. It also took 3K less 6809 code, which mattered, as you'll see.

      Pass 2 needs its own check. If your source later changes a defs symbol (OS9.D set 2), reading the defs again in pass 2 would see the new value. Every change to a symbol goes through symtab.c's setters (phase 8), so the setters report any change to a defs symbol after the image was loaded. In that case pass 2 reads the defs normally. That is always right, because pass 1 left exactly the state reading would have left.

      Testing it

      harness/imgcheck.py assembles all 290 build commands three times: without an image, recording one, and loading it. Object bytes, messages, exit status and the symbol table must be the same all three times, and they are: 290 of 290. With one image file shared by every job, most loads must refuse it, and again 290 of 290 come out the same. --variants builds 14 cases around echo.asm that must or must not load: -DH6309 added or changed, os9.d touched, a source that changes a defs symbol, one that defines a defs name first, one without its own nam. Each is checked against plain assembly as well as for the right decision.

      The result

      In the host model, echo.asm on the 6809 went from 33.7 million instructions to 5.3 million, the same module, and window switches halved (12,025 → 5,868). Recording costs a little extra once (37.6 million).

      On the emulated F256, the 57 commands in level1/cmds took 1,556 seconds without an image and 667 with one, every module identical to the Linux build's. That is 2.3 times faster, not 6. The model counts a window switch as one instruction, but on the machine each is two system calls, and loading still makes about 5,900 of them, because adding a symbol walks its bucket's tree across blocks. So the next thing to speed up is the switching, not the parsing. Measuring both ways is what showed that.

      Fitting it in

      The new code first made las 42,906 bytes. A Level 2 module in five 8K slots must end by $FD00, so it can be at most 40,192 bytes. One byte more takes a sixth slot, and then F$Fork can't fit las's two data blocks and its window (chapter 11). Three things brought it to 40,168:

      • the simpler validity rule above;
      • short wrappers. In DCC's code every call that passes the file pointer and a long position costs 10 to 20 bytes, so seek(pos) and friends are written once;
      • no stack checks in five files that never recurse. Each C function normally starts with a call to _stkcheck (6 bytes). The symbol accessors are also las's busiest functions, so this alone saved 1.4 million instructions on echo.

      A bug the optimizer made

      The first native test loaded nothing. The model's breakpoints showed the image being read from the wrong place, and the cause was in code DCC generated from a two-line function:

      long tell () { return ftell (Fp); }

tell pshs u            tell pshs u
 ldd Fp,y               ldd >Fp
 pshs d                 pshs d
 lbsr ftell             lbsr ftell
 leas 2,s               puls x,u,pc
 puls u,pc

      On the left is the compiler's output, on the right the optimizer's. The optimizer is a peephole optimizer: it looks at a few instructions at a time and replaces known patterns with shorter ones. Here it turned "drop the argument, return" into "pop the argument into X, return", which saves 2 bytes. That's safe when a function returns an int, because the result is in D. But DCC returns a long by leaving X pointing at it, and the shortcut overwrites X. No function in the six tools had hit this pattern before. defsimg.c now stores the position through a pointer instead, and the hazard is noted in DESIGN.md §10. (The ldd >Fp on the right is fine: in Level 2 a program's data starts at address 0, so Y is 0 and >Fp is the same address.)

      Fixed in step 14, at no cost. When we came back to it, the bug turned out to be wider. It isn't only a call's result: any function returning in X is hit if exactly 2 bytes are left on the stack when it returns. One int local and a conversion are enough:

      long f3 (a) int a; { int b; b = a; return (long) b; }

 lbsr _litol            (X points at the long)
 puls x,u,pc            (and here it's gone)

      The optimizer can't tell which functions return in X; only the compiler knows the type. Removing the pattern wasn't an option either: it saves 2 bytes in thousands of int functions, and dcc68 itself had only 29 bytes to spare. So dcc68 now avoids handing the optimizer the dangerous pair. When a result is in X and 2 bytes must come off the stack, it pops them into D with puls d. That's as short as leas 2,s, and D holds nothing in a function that returns in X. A new optimizer rule then joins puls d and puls u,pc into puls d,u,pc. That's always valid: the 6809 pulls registers in a fixed order, D before U before PC, whether you write one instruction or two. The broken function ends in puls d,u,pc, the same 2 bytes as the broken puls x,u,pc, and now it's right. A test program, harness/native/longret.c, printed three wrong results with CoCoC's compiler and none with ours, at the same size, and the F256 builds and runs it in every test run.

      Two side stories. Comparing the compilers over all of CoCoC's C sources found 14 places where the change applies, and none of them was a broken return, so CoCoC's own libraries never hit the bug. And the 40 lines that do the job made dcc68 43 bytes too big for its six blocks. The room came from messages: in DCC's code, every place that passes a string literal stores its own copy of the text, so error("storage error") written three times costs about 75 bytes. One small function that makes that call, used three times, costs about 35. DCC already did this for one message (multidef()); three more did it for the rest. dcc68 ended 17 bytes under the limit.

      CHAPTER 10Testing against lwasm

      How do you prove a new assembler is compatible with an old one? Not by reading a list of features. You give both the same input and compare the output, byte for byte, over as much real code as you can find. This is called differential testing. The trusted tool, here lwasm, is the reference: whatever it produces is correct by definition.

      The harness, harness/lwdiff.py, does this for the whole Level 2 F256 build.

      Getting the real commands

      The harness doesn't guess which files to assemble or which options to use. It asks make. Running make -n -B in the recipe directory is a dry run: make prints every command it would run, for every target, without running any of them. The harness reads that output and picks out the 290 lwasm commands, along with the directory each one runs in.

      Then, for each command, it assembles the file twice: once with lwasm exactly as the build would, and once with las using the same source, include paths and -D definitions. It compares the results and sorts each file into a status:

      StatusMeaning
      MATCHSame bytes as lwasm. The goal.
      DIFFAssembled cleanly, but the bytes differ.
      ERRORSlas reported assembly errors.
      FATALlas stopped early, for example because it couldn't open a file.
      ASSEMBLEDAn object-format file assembled. Its bytes can't be compared directly (LWOBJ versus ROF), so it gets compared after linking, in phase 5.

      First errors and knock-on errors

      The first run, before any changes to las, matched 0 files out of 290. That was expected. More useful is why each file failed.

      scfg.asm produced 1,868 errors, but only the first one matters. Its first error is mod, which RMA doesn't know. Because mod failed, RMA thinks it's outside any code section, so it rejects rmb, lda, rts and everything after as “bad mnemonic”. Those 1,867 later errors are knock-on errors: symptoms of the first one, not separate problems. Fix the first error and they disappear.

      So the report ranks problems by first error. These were the top results in the baseline:

      First errorFilesCause
      bad mnemonic: mod126Module format isn't supported yet. Phase 3.
      bad label74Lines like ;;; ASC_BIN. lwasm treats ; as a comment; RMA only accepts * at the start of a line.
      bad mnemonic: fcb21Data files with no section around them. RMA only allows data inside psect/vsect.
      bad mnemonic: section21lwasm object format. Phase 5.
      can't open "defsfile\r"18These files have Windows line endings. lwasm drops the carriage return; RMA keeps it as part of the file name.

      Why this finds things you wouldn't think of

      Before the harness ran, the compatibility list in the design doc had local labels, fill, ifndef and the shift operators. Nobody listed ; comments or Windows line endings, yet together they stop 97 files. Differences like these are invisible until real code hits them, which is why the test runs over the whole build and not a hand-picked sample.

      Each run also adds a line to harness/reports/history.csv, so the project's progress is a count you can watch: 0 of 290 today.

      Holding the test still

      A measurement only means something if just one thing changes at a time. If the NitrOS9 source changed between two runs, a new match could come from a fix in las or from an edit in NitrOS9, and you couldn't tell which. So the harness doesn't read your working copy of NitrOS9. It assembles corpus/, clones of your devsys branches pinned to exact commits listed in harness/corpus.lock. Moving to newer NitrOS9 is a separate, deliberate step, and every report records which commits it ran against.

      Testing a change that shouldn't change anything

      Comparing against lwasm shows progress, but it can't check a refactor like phase 1, because nearly every file fails anyway. A refactor needs a different question: does the new las do exactly what the old las did? That's regression testing, and harness/regress.py does it. It builds the last committed las as the reference, runs both versions on about 740 inputs, and compares everything they produce: object file, listing, symbol table, error messages and exit code. Any difference fails.

      The inputs are code RMA already handles: 252 hand-written RMA source files, plus 198 C files compiled to assembly by DCC. That's real compiler output, and 430 of these assemble cleanly, so the test exercises working paths, not just error messages.

      Two lessons from building it:

      Prove the test can fail. A test that has never failed might not be checking anything. So before the refactor, I made a deliberate small change (32 hash buckets instead of 64) and confirmed the test caught it: 617 of 740 files changed. This is called a negative control. Only then is “740 of 740 identical” worth something.

      Make sure the test doesn't disturb itself. The first run failed with no code changes at all. The assembler writes macro expansions to a scratch file with a fixed name, rma.tmp, in the current directory. Running the old and new versions side by side in the same directory let them overwrite each other's scratch file. The fix was to give every run its own empty directory. It also revealed a real problem to fix later: two assemblies in one directory on the F256 would collide the same way.

      A new source in main: one directive, three names

      Your pull of NitrOS9 main on 2026-10-12 brought diag, a 28,656-byte hardware test, and lwdiff found the one line of main that las couldn't read, in level1/wildbits/cmds/diag_hw.asm:

                          zmb NtpLen-1

      zmb is lwasm's “zero memory bytes”: put this many bytes of zeros here. RMA has the same directive under the name rzb, and lwasm also accepts bsz. So the fix (D48) adds no new code path. In lwasm mode only, las looks up zmb and bsz as another directive it already has, and RMA sources see no new names. Which directive depends on where the line is. In a module it is rzb, which writes the zeros. Inside a section it is that section's rmb, which writes zeros in a code section but only reserves space in a bss section. A bss section has no bytes in the file at all, only a size, so “zero bytes” there means “space the program will get, which OS-9 clears”. lwasm does the same, and a quick test showed it: buf zmb 3 in bss is 3 bytes of reserved space in both assemblers. Now all 217 of main's modules match lwasm, diag included. lwasm needs 65 seconds for diag, and las 0.13 seconds, with the same bytes.

      CHAPTER 11Running on the F256

      Everything so far ran on Linux. The goal is to run the tools on the F256 itself. This chapter covers how they got there (phase 7), what broke on the way, and how we test programs on a machine we can't easily watch.

      Cross and native

      A native compiler runs on the machine it makes code for. A cross compiler runs on one machine and makes code for another. Our Linux build of DCC is a cross compiler: it runs on a PC and writes 6809 assembly.

      That solves a chicken-and-egg problem. To compile las on the F256 you need a C compiler running on the F256, and DCC itself is a C program that needs compiling. Making a tool build itself is called bootstrapping, after pulling yourself up by your bootstraps. The usual way out, and ours, is to cross-compile the first native version on a machine that already has the tools.

      native/GNUmakefile does that. Each C file goes through the same four passes the dcc driver runs on the F256: dcpp (preprocessor), dcc68 (compiler), dco68 (optimizer) and las (assembler). Then rlink joins the objects with CoCoC's cstart.r and C library. Only the machine running the passes differs. The six tools it builds:

      Two rules we found by measuring. dcc68 first ran out of memory on a one-line program.       • A module in 6 blocks may be at most 48,384 bytes: it must end by $FD00. On this NitrOS9 the top 768 bytes of every process are reserved. One byte more and the module takes a 7th block. On a CoCo 3 the reserved part is the top 512 bytes, which is presumably why CoCoC's 48,521-byte dcc68 was fine there.
      • F$Fork won't start a process whose module and initial data fill all 8 slots. A running process can still grow to all 8 with F$Mem, which is what las does above.

      So dcc68 now starts with a small data area and grows it with sbrk. It is compiled without stack checks and without profiling support, and the optimizer's Level 2 patterns shrink it a little more. Those patterns use a Level 2 fact: a program's data starts at address 0, so the data pointer Y is always 0, and leax >1234,y (4 bytes) can become ldx #1234 (3 bytes). The result is 48,290 bytes, 94 under the line.

      Old C, new surprises

      DCC compiles K&R C, the language before the 1989 standard. Code that gcc accepted without a murmur broke in ways only the 6809 build could show.

      One namespace for every structure member

      In K&R C a structure member's name isn't tied to its structure. x.name means "the bytes at name's offset from x", whatever x is. RMA's C source has a 6809-only line in las/rma_main.c:

      MLCod.q_long = 0;    /* meant: MLCod.opers.q_long */

      q_long belongs to a union inside MLCod, at offset 2. Written this way it means offset 0 of MLCod, so it cleared the opcode that had just been stored there. Every ends directive became opcode 0, which is rmb, and rmb wants an operand:

      *** error - bad operand ***
00066 0081                     endsect

      gcc never saw the line: it sits under #ifdef COCO. The same rule made DCC reject a structure in rlink's lwsel.c, whose member refs clashed with another structure's refs at a different offset.

      Arguments with no prototype

      A prototype declares a function's parameter types, so the compiler can convert each argument to the right type at the call. K&R C has no prototypes. The caller pushes each argument as it is and the function reads what it expects. In las/directives.c:

      savcurorg (CodeAddrs + NmbrInt);

      On the 6809, NmbrInt is a long (4 bytes) and savcurorg takes an int (2 bytes). The caller pushes 4 bytes and the function reads the first 2. The 6809 stores the high half first, so for any small number the function reads 0. Every rmb in a vsect reserved nothing, and the data size in the ROF header came out 0. gcc can find this kind of bug: -Wtraditional-conversion warns wherever a prototype changes an argument's width. Run over a copy of the source where those values are long on Linux too, it found two places, both now fixed.

      The rest was ordinary porting: no void keyword, no atexit() or ftruncate() in CoCoC's library, and a header search order that found the system's ctype.h instead of the optimizer's own.

      A small model of OS-9

      MAME takes a couple of minutes per round trip and shows only the end result. So harness/os9run.py models one OS-9 process on Linux. A 6809 emulator (cpu6809.py from your Tempest port) runs the module. Whenever the program makes a system call, the script answers it with a Linux file: I$Open, I$ReadLn, F$Mem and the rest. It reproduced every MAME failure in about a second. Given rlink's link map, it also says who called what:

      break e_report: get_param+278 <- get_param+8 <- do_math+13 …

      That is, something was evaluating an expression for endsect. It led to the q_long bug in minutes. The model's limits are also a lesson. It answers system calls the way the script says, so it can't find a limit it doesn't model. It happily gave dcc68 a second data block that the real kernel refuses. Use a model to find bugs quickly; take the verdict from the real thing.

      The model can also be wrong in the other direction. In phase 10 it said native las expanded nested macros wrongly. MAME said they were fine. The bug was in the model: it answered "how big is this file?" (SS.Size) from Linux's file size, while Python still held the program's last writes in its own buffer. Fixed by flushing first, but the lesson stands: when the model and MAME disagree, believe MAME.

      Testing on the emulated F256

      harness/native.py is the real thing, short of hardware. It copies a Jr2 disk image, installs the tools, libraries and headers, puts the test inputs on it, and writes a startup file. MAME boots the image and the shell runs startup. When the last line writes a marker file, the script copies the results off the image and compares them with the host tools' output. Today:

      • native las assembles all 56 assembly files of the toolchain's own C sources, byte for byte the same as Linux las;
      • native rlink links rlink, dcc, dcpp and dco68, identical to the Linux links;
      • native dcc compiles and links a C program through all five passes on the F256, and the program runs.

      Where the disk comes from

      The disk image is a NitrOS9 boot disk: the kernel, drivers and commands, built by a NitrOS9 recipe, the makefile for one machine's disk (recipes/wildbits/l2 for the F256). Since 2026-10-11 devsys builds its own, from your NitrOS9 main tree, which has the rc24 memory map the updated MAME expects. boot/wildbits/l2/makefile includes main's own l2 recipe, so the disk has whatever main builds, and adds three things the toolchain wants: PipeMan, Piper and Pipe for pipelines, and /nil for dcc -w. The test suite now checks both.

      One make detail made this take three extra one-line files. A makefile that says include ../../rules.mak means "relative to the directory make is running in", not "relative to this file". NitrOS9's recipes rely on sitting exactly two levels below recipes/. Our recipe sits at boot/wildbits/l2 instead, so its ../../rules.mak is boot/rules.mak, and that file contains one line that includes main's real one. boot/libs.mak and boot/wildbits/wildbits.mak do the same. NitrOS9's own makefiles stay untouched, and every build output lands in devsys.

      One OS-9 detail cost a run: the shell's > and >> create their file, and creating a file that already exists fails with ERROR #218. Two commands that both wrote their errors to err meant the second never ran.

      Two more limits appeared with NitrOS9's long command lines. The shell reads at most 200 characters of a line; the rest runs as a second, broken command (WHAT?). And a C program's start-up code, cstart, splits its arguments at commas as well as spaces, so --pragma=pcaspcr,nosymbolcase arrives as two words. las now accepts --args=FILE, which reads the arguments from a file, and that sidesteps both.

      Running suites side by side. MAME emulates one 6809 on one PC core. The full NitrOS9 run, 200 module sources at about 40 seconds each, took two hours in one MAME. native.py --shard K/N takes every Nth file starting at K, and --work DIR gives each run its own disk image and output, so 8 MAMEs on 8 cores do it in 22 minutes. Splitting a big job into independent slices like this is called sharding. It works here because no file's result depends on another's.

      Building NitrOS9's programs on the F256

      Phase 10's goal is the other half of the Level 2 build: the 13 programs written as lwasm object files (sysgo, grep, telnet, play and the rest) and the three libraries they link against. The obj suite does what the real build does, on the F256:

      1. Assemble lib/wildbitsl2.as. It holds only constants (2,074 of them: system calls, error codes, hardware addresses), in a _constant section.
      2. Assemble the other 89 object sources, each with --defs=wildbitsl2.o, so las knows those constants (chapter 6, "Values only the linker knows"). las keeps them in its banked blocks next to the symbols (chapter 9): in its ordinary heap they took 30K, and every file failed with symbol table overflow.
      3. Build libwildbitsl2, libnet and libalib. A ROF library is just its members one after another, so the OS-9 merge command builds one: merge a.o b.o c.o >lib.l. libalib has 75 members, too many for one 200-character line, so the suite merges them in groups and then merges the groups.
      4. Link each program with rlink --lwlink, the libraries in the build's order.

      Each object must equal the one Linux las/build/nosz makes from the same files, and each program the one Linux rlink links from those objects. One file needs care: wbinfo uses dtb, which writes the date and time of assembly into the program. Two runs a minute apart differ in those bytes (and in the module's CRC), so the check masks them.

      Getting there took several fixes. Each one is a kind of bug that only shows up on the real machine, so each is worth knowing.

      A char comes back in half a register

      A calling convention is the agreement between a function and its callers about where arguments and results go. DCC's says: a function returns its result in D, the 16-bit register made of A (high byte) and B (low byte). A function returning a char sets only B. Its caller has to widen the byte itself if it needs 16 bits, with sex (sign extend: copy B's top bit through A) or clra.

      dcc68 forgot that in one case: a char function used directly as a condition. Here is docs/learn/examples/charcond.c through CoCoC's own dcc68:

      char next();
skip() { if (next()) return 1; return 0; }

 lbsr next
 std -2,s      store D below the stack: sets the Z flag from all 16 bits
 lbeq _2

      std -2,s is DCC's trick for testing D: storing a register sets the flags. But A holds whatever the callee left there. In las, SkipSpac() ends with ldb 0,u, and A still held $FF from the stack check at its start. So if (SkipSpac ()) in csectsetup was always true, las tried to read a number from an empty operand, and native las rejected section _constant with "bad operand". The fix in dcc/CC09/bool.c tests B instead:

       lbsr next
 tstb          test the byte the function returned
 lbeq _2

      Only that one line in all six tools changed, and none of CoCoC's own sources, so the bug had been there since CoCoC and simply never mattered. On Linux the same C is compiled by gcc, which knows the rules, so only the 6809 build could show it.

      Two files, one buffer

      C's buffered I/O (stdio) reads a file a block at a time into a buffer and hands out bytes from it. CoCoC's library gives each open-file slot a buffer the first time it is used, with ibrk, and keeps that buffer for the slot's whole life, through fclose and freopen. The size it allocates is whatever _bufsiz says at that moment.

      rlink's original OS-9 code sets InFile->_bufsiz = 1024 after every freopen. That is only safe if the buffer is allocated afterwards. In a --lwlink link the input slot had already been used with the default 256 bytes, and the output file's buffer had been placed right after it. The model showed the overlap directly:

      InFile   base=$0797  end=$0B97   (claims 1,024 bytes; really owns 256)
OutFile  base=$0897  end=$0997   (inside InFile's claimed range)

      Writing sysgo's code to the output overwrote the input buffer, so the next object's reference names were read out of machine code ("symbol The device isn't ready not found"). rlink now sets the size only while the slot has no buffer. las had the same pattern for its macro work file and got the same guard.

      When the stack meets the heap

      A C program's data area holds three things: its static variables at the bottom, the heap (memory handed out at run time by malloc and friends) growing up from them, and the stack growing down from the top. CoCoC's start-up code checks at every function entry that the stack still clears the heap. If not, it prints **** STACK OVERFLOW ****, even when the real cause is a heap that grew.

      That message stopped llwbsd, the one module source of 200 that failed natively. Its macros make las open its work file, whose 512-byte buffer comes out of the same gap, and las had been linked with no extra room. rlink's -M=16 adds 4K. It costs nothing: las's data already takes two 8K blocks, which had room to spare.

      A shortcut that outlived its pointer

      RMA's 6809 build wrote each reference record (type byte and 16-bit offset) by dumping the 3-byte structure straight from memory: fwrite (sref, 3, 1, OutFile). Phase 8 turned sref from a pointer into a handle, a number that only means something to symtab.c. The line still compiled, and wrote 3 bytes from whatever address the number happened to equal. Every external reference native las wrote came out as type 0, offset 0.

      The Linux build uses the portable branch of that #ifdef, so no Linux test could see it. The las suite in MAME would have caught it in a minute, but phase 8 ran only the suites it thought the change affected. Now every suite runs after every change to a native tool.

      Measure where the memory goes

      The last problem was plain size. Linking a program against libwildbitsl2 made native rlink hold all 2,074 constant names, and play, the largest program, still ran out after that was fixed. Counting every allocation in the model showed where it went: 19K went to malloc for the table rlink uses to choose library members, and was freed before linking. But rlink's own allocator used sbrk, which takes fresh memory from the top and can't reuse what malloc has freed. Switching rlink to malloc lets the link reuse it, and play now peaks at 24.5K. The same measurement showed the member table reserving room for 512 modules (13K) when the link has 77; it now grows as needed.

      A make for the F256

      A program built from several files needs something to remember which file is made from which, and to redo only what an edit affected. That is make. A makefile lists targets and what each depends on; make compares the files' dates and runs the commands for every target older than one of its inputs. This is the one the F256 now has, a test project from harness/native/make:

      OBJS = main.r util.r dbl.r

prog: $(OBJS)
    $(LINK) $(OBJS) -f=prog

      The makefile never says how to make main.r from main.c, or dbl.r from the assembly source dbl.a. Those are default rules, in a text file make reads first, /dd/SYS/make.default. That file is why we chose CoCoC's make, Tim Koonce's public-domain one, over Microware's own: NitrOS9 also has Microware's make (as a disassembly, nitros9-languages/ccompiler/make_dis.asm), but its rules are built into the program. Ours were edited to say dcc and las:

      .c.r:;$(CC) $(CFLAGS) -r=$(RDIR) $<
.a.r:;$(RMA) $(RFLAGS) $< -o=$(RDIR/)$@

      In MAME the F256 builds the project, runs it ("prog: 5 42"), and after touch util.c recompiles only util.c and relinks. With a syntax error in util.c it stops before the link, which works only because the tools now report failure honestly (step 14).

      Dates to the minute. OS-9 records a file's date to the minute, not the second. Make rebuilds a target that is not newer than its input, so a tie counts as "out of date". Something built in the same minute as its inputs is therefore rebuilt by the next make in that minute. That's wasted work, never a wrong result; the other way round, treating a tie as "up to date", could skip a change made in that minute. The test waits a minute between steps (sleep 3700: OS-9's sleep counts ticks, 60 a second).

      The test also found an OS-9 habit worth knowing: copy gives the new file the original's date. Copying an old version of a source over a new one makes it look older than its .r, and make skips it. touch after copying sets the date to now.

      Taking it to the real machine

      Everything so far ran in MAME, on the Jr2 image. MAME proves the outputs are right. It can't prove the hardware behaves the same: real block-switch timing, the SD card, the RAM a running system leaves free. Your machine is a K2, and the Wildbits MAME only emulates the Jr2. So the card goes through a fixed loop, the same one your port guide uses for games:

      1. harness/card.py build copies your K2 boot image and adds the toolchain: the six tools in /dd/CMDS, CoCoC's C libraries in /dd/LIB and headers in /dd/DEFS, a /dd/TMP, and /dd/DEVSYS with test sources and a script, selftest.
      2. card.py mame builds the same card from the Jr2 image and runs selftest in MAME first. A card that fails in MAME would fail on the machine too, and the emulator says why.
      3. You write the card with dd, boot the K2 and type /dd/DEVSYS/selftest.
      4. You read the card back with dd, and card.py check compares every result with what the Linux tools make.

      selftest is a procedure file: a text file of shell commands with the execute attribute set. When you type its name, the shell sees it isn't a module and runs its lines itself. It builds and runs hello.c with dcc, assembles eight level1/cmds sources without and with a defs image, and writes the time between steps with date -t. Every output goes to a new file in /dd/DEVSYS/R, because OS-9's shell won't redirect into a file that already exists (error #218). In the MAME rehearsal, the eight modules took 190 seconds without an image and 84 with one, all identical to the Linux build.

      Then you ran it on the K2 (2026-10-05). card.py check found every result identical to the Linux tools': hello compiled and printed its line, and all eight modules matched, with and without the image. The K2 built hello.c in 4 seconds and the eight modules in 158 seconds without an image and 70 with one. That is about 17% faster than MAME's Jr2. Everything earlier in this chapter was proven in an emulator, and now it is also proven on the machine itself.

      A second card carried the one-block las from step 12 (below) and two memory reports. mfree lists the free blocks of physical RAM, and mmap draws all of them, one character per 8K block. Your K2 has 1,656K free with NitrOS9 running: 207 blocks. The count was the same after the test, so every tool gave its blocks back when it exited. las can hold at most 15 symbol blocks, 120K, so even several assemblies at once would leave most of that memory free.

      One program, several processes

      las now fills its 64K: five 8K slots of code, two of data, one window for the symbol blocks, and 24 bytes to spare. The F256 has 1800K, but one process sees only 64K of it. There are two classic ways out.

      The first is an overlay: load one part of the program's code over another while it runs. Our C compiler and linker have no support for that. A call into another module would need a jump table and a shared data pointer, and most of las is needed all the time anyway.

      The second is the OS-9 way: split the work between processes. OS-9 programs are reentrant: the code never changes itself and keeps all its variables in the data area. So any number of processes can run one copy of a module in memory, and a second process costs only its own data blocks. F$Fork starts one. Unlike Unix fork, it doesn't copy the parent. It starts a fresh process from a module, with its own 64K. That is how Microware's cc ran its passes, and how our dcc driver runs dcpp, dcc68, dco68, las and rlink.

      The processes can share memory, too. F$MapBlk maps any block number you give it into your map. It doesn't check which process allocated the block (level2/modules/kernel/fmapblk.asm). So a child that knows the numbers of las's symbol blocks can read the symbol table directly, with a pipe for the control messages. That gives two plans, recorded in DESIGN.md:

      • Native sizing. On Linux, lwasm's ,pcr sizing runs a trial pass in a fork()ed child (chapter 4). On the F256, las could F$Fork a second copy of itself for the trial. It's cheap in memory, but the trial's code must fit in las's own 64K, so it needs room first. (Done in step 13, below.)
      • Room. Move a self-contained job into a smaller helper program. Reading the --defs library is one: the helper could write a defs image, which las already knows how to load.

      Measure first: where a C program's data goes

      Step 12 needed one number before choosing: how much of its two data blocks las really uses. A program built with CoCoC lays out its data area in four parts, set up by cstart (CoCoC's start-up code, which runs before main):

      • Static data: every global and static variable, at fixed addresses from $0000. The link map's end symbol marks where it stops.
      • The ibrk heap, from end upwards. ibrk(n) hands out the next n bytes and moves _mtop up. It never gives memory back. CoCoC's stdio takes each file's buffer from here: 256 bytes for a disk file, 128 for a terminal.
      • The stack, from the top of the data area downwards. Every function call pushes its return address and local variables.
      • The sbrk heap, above the stack. sbrk(n) asks OS-9 for more memory with F$Mem, which makes the data area bigger.

      The heap and the stack grow towards each other. CoCoC guards the meeting point: ibrk refuses to cross the stack's lowest reservation, and every function compiled with stack checks tests that the stack hasn't reached _mtop, printing STACK OVERFLOW if it has.

      The OS-9 model (harness/os9run.py --stats) now records the lowest stack pointer, the function running at that moment, and _mtop at exit. We ran native las through it on 348 inputs: the 200 NitrOS9 module sources, the 90 object sources and the tools' own 58 compiler outputs. SecNames gives each section name a number, so the ,pcr sizing can tell whether a label is in the same section.

      One block of data, six of code

      With the numbers in hand, the choice between the two plans was easy. A helper program could take out the 1.5K --defs reader. Fitting the data into one 8K block frees a whole slot for code: las may then be up to 48,384 bytes, the same limit as dcc68. That is 8K of room instead of 24 bytes. Four small changes did it (DESIGN.md D37):

      • CondBits holds 2,048 conditionals: 256 bytes, still twelve times the corpus's most. Going over stops with too many conditionals, as before.
      • SecNames keeps 32 pointers, and each name gets exactly its own length from the heap. This also fixes a bug nobody had hit: a section name of 32 characters or more overran its row.
      • las's own heap allocator, getmem (las/labels.c), uses ibrk instead of sbrk. In one block nothing can grow the data area, because the module, the data and the symbol window would fill all 8 slots. With ibrk, macros, file names and stdio buffers all share one gap below the stack.
      • The extra memory rlink adds to the data area (las_MEM in native/GNUmakefile) went from 16 pages to 8. The data size in the module header plus a 200-character command line now always fits in 8,192 bytes.

The stack check prints STACK OVERFLOW. The module also got 89 bytes smaller, because sbrk's code is no longer linked.

      Sizing on the F256: a child that starts from the top

      Until step 13, las on the F256 gave every ,pcr operand its long form, so a module it built could be a few bytes longer than lwasm's. The trial run of chapter 4 needs a second process, and on Linux that is one call: fork() copies the running program, memory and all, and both copies carry on from the same line. The child is the trial, and the parent waits for its answers.

      OS-9 has no such call. F$Fork starts a program from its first instruction, with a fresh data area and a parameter line, like typing its name at the shell. So las runs itself: it passes the child its own arguments plus a hidden one, --sztrial=N. The child reads its options, loads the --defs files and defines the -D symbols again. With one source file that leaves it exactly where the Linux child starts. Then it runs the trial pass 1, decides with lwasm's rule, and exits. The module is already in memory and reentrant, so the second process costs only its own data and symbol blocks.

      The answers need a way back: one byte per ,pcr site, short or long. Unix would use a pipe, and OS-9 has pipes too. But your F256's boot file has no PipeMan, Pipe or Nil modules (we listed the modules in OS9Boot on both images), so there are none to open. We used the trick from "One program, several processes" above instead. Before forking, the parent asks for one 8K block of RAM with F$AllRAM, and N is that block's number. The child maps block N with F$MapBlk, writes SZ, the count and the answers, unmaps it and exits. The parent maps the same block and reads them. That is shared memory: two processes see the same physical RAM, because each maps it into its own 64K. The block also carries the child's parameter line on the way out, which saves 400 bytes of stack.

      parent
      F$AllRAM: block N. Write "args --sztrial=N" into it. F$Fork las. F$Wait.
      child
      options, --defs, -D again; trial pass 1; decide; F$MapBlk N; write "SZ", count, answers; exit 0
      parent
      F$MapBlk N; one bit per site into its own memory; F$DelRAM N; pass 1 and 2 for real

      Even with PipeMan installed, the block would still be the better choice. A pipe hands bytes over one at a time through the pipe manager, and it gets tricky at the edges. If the parent reads before the child has opened the pipe, PipeMan sees nobody who could write and reports end-of-file (level1/modules/pipeman.asm). If instead the parent waits for the child to finish before reading, a child with more answers than the pipe's buffer holds blocks forever, waiting for a reader that is waiting for it. The block has neither problem and works on any boot. Pipes can't help las or rlink elsewhere either: las reads its source twice and rlink jumps around in its input, and a pipe can only be read once, front to back. The one place they could help is dcc, which passes each pass's output to the next through a temporary file. Streaming them would save some card reads and writes, but not much of the 6809's time.

      The trial writes down every ,pcr site and every code label, and cbmfont alone has 2,480 labels. That doesn't fit in the 869 free bytes of step 12's one data block, so the notes go into banked memory like the symbols, in chunks of 128 sites or 512 labels. The same code runs on Linux, so every Linux test also checks it keeps to the one-window rule of chapter 9.

      One case needed thought. When the child loads a defs image (chapter 9) instead of reading the defs, the labels in the defs never pass through the code that notes "this is a code label". If a ,pcr ever pointed at one of them, the child couldn't decide. It then exits with status 3, and the parent runs it again with --sztrial=N,n, which tells it to read the defs. The corpus never needs that, but the rule keeps the output exact without depending on luck.

      The emulator caught a bug of its own on the way. In os9run.py, a mapped block is a copy, written back when it is unmapped. The parent still had block N mapped while the child ran, so its stale copy overwrote the child's answers when it unmapped. On the real machine both see the same RAM, so the model was wrong, not las. Now the model writes the parent's mapped blocks back before running a child and reads them again after.

      The result: in MAME, native las assembles 199 of the 200 NitrOS9 module sources (all 200 since struct arrived, chapter 4) and all 90 object sources byte for byte like Linux las with sizing, which is to say like lwasm. The 13 programs link the same. The price is time. Every lwasm-mode assembly now runs pass 1 twice: the 57 level1/cmds took 2,505 emulated seconds without an image (1,555 before) and 1,145 with one (667 before). las grew from 40,090 to 43,420 bytes, well inside its 48,384.

      Then you ran the third card on the K2. All eight modules matched Linux las with sizing. One of them proves it: copy has two ,pcr operands, one of which lwasm makes short, so its module is 1,469 bytes with sizing and 1,470 without, and the K2 made the 1,469-byte one. The eight took 255 seconds without an image and 120 with one (157 and 70 before sizing). All 207 free blocks were still free afterwards, so the parent always gives the shared block back.

      Where the time goes: measure, then read the defs once

      Step 19 is about speed. The obvious suspect was the sizing trial: it runs pass 1 a second time. Before changing anything we measured where the time actually goes. os9run.py, our 6809 model, gained two options. --mark sz_pass prints the instruction count each time a pass starts, so a run splits into its passes. --profile counts the instructions executed in each function. This is a profile: instead of guessing, you see which code the processor spends its time in. Here is native las on level1/cmds/attr.asm, without an image:

      Part of the run6809 instructions
      sizing trial (the child's pass 1)21.4M
      the parent's pass 121.0M
      pass 218.1M
      deciding the sizesalmost nothing

      The sizing rule itself is cheap. The three passes cost about the same, and more than half of each goes to reading lines: getsrcline, getc, and FindCmd, which looks up each line's directive. But attr.asm has only 312 lines. What else is being read?

      The defs. attr.asm says ifp1 / use defsfile, and defsfile pulls in os9.d, scf.d, rbf.d and wildbits.d: 3,081 lines of equates. In RMA, ifp1 means "only in pass 1", so pass 2 skips them. lwasm doesn't have that idea. It reads each file once and treats ifp1 as always true, so las in lwasm mode does the same (is_pass1 in las/directives.c). Pass 2 even replays pass 1's answer to every conditional (cond_log, chapter 4), so it reads exactly the same lines. The result: three passes, three readings of 3,081 lines, to assemble 312.

      A second reading of the defs learns nothing new. Every equate gets the value it already has. Chapter 9's defs image is built on that fact: it records what the defs did and loads that instead of reading them. But you have to ask for an image (--defsimg=FILE), and it lives in a file, with dates and checks to make sure it still fits. Within one run nothing can go stale. So now, without an image, las records the defs in memory during pass 1, using the same rules the image uses to decide what may be recorded. Pass 2, and any settling pass, apply that record instead of reading the files.

      What does the record need to hold? Less than an image, because the symbols are already in the table: pass 1 made them. It needs the counters the defs moved (the lines read, the local-label blocks, how many conditionals to skip in the replay log), the last nam and ttl, and which symbols the defs created. To find whether anything else changes, we looked at what a second reading changes in the 30 images imgcheck makes. It is always one bit. When a line uses a symbol before its definition, pass 1 marks the symbol DIRLOC, "referenced before defined". Pass 2 clears that mark on each label it reaches. os9.d starts with exactly that case, its include guard:

                          IFNE      OS9.D-1
OS9.D               SET       1

      So applying the record clears DIRLOC on the defs' defined symbols, and the symbol table ends up bit for bit as if pass 2 had read the files. If the source changes a symbol the record depends on, the next pass reads the defs as before.

      Results: attr's pass 2 dropped from 18.1M to 2.6M instructions. The 57 level1/cmds in MAME went from 1,647 to 1,352 emulated seconds without an image (18% faster), with the same output and every test passing. With an image nothing changes (788 s), because the image already skipped the defs. The trial child still reads the defs, because it is a separate process with no pass 2. The next step removes the child: the trial becomes the parent's own pass 1, so the defs are read once in all.

      The trial without a child

      Why did the trial need a child at all? Pass 1 leaves a lot behind: every symbol defined, every macro stored, the conditionals' log. The real pass 1 had to start from a clean slate with the decided sizes, and resetting all that state by hand is fragile (phase 4 tried it). A child is a clean copy for free. On the F256 that freedom wasn't free: F$Fork starts las from the top, so the child redid the start-up and read the defs again.

      But las already had a way to correct values without starting over: the settling pass of chapter 4. It runs pass 2's code without writing anything, and pass 2's code fixes each label it reaches. So now pass 1 is the trial. Every ,pcr gets its long form, the trial records what lwasm's rule needs, and at its end sz_finish decides. If nothing became short, pass 1's layout is already the final one and pass 2 follows directly. That holds for 240 of the 290 corpus assemblies, because lwasm's rule leaves most ,pcr operands long. If something became short, every label after it is too far on, and settling passes run until nothing moves: two for copy, which has one short ,pcr.

      Two passes of pass 2's code in a row exposed something pass 2 had always relied on. When pass 1 meets a symbol before its definition, it doesn't know the value, so it picks the long form (extended addressing) and marks the symbol DIRLOC. Pass 2 sees the mark and picks the long form too, or the code would shift between passes. When pass 2 reaches the definition it clears the mark, because later uses were backward in pass 1 and were sized by value. A second pass of pass 2's code then finds no marks and sizes the early uses by value: a different length. So settle notes pass 1's marked symbols and sets the marks again before each pass. Chapter 4's settling had the same weakness, unnoticed because the 16 files of main that settle never hit it.

      The regression test found a second, smaller one: the listing's first page header. Pass 2 prints it with the title the previous pass left. Pass 1 keeps the first nam and ttl it sees, a settling pass keeps the last, so 40 listings showed rbf.d's title instead of the program's. The titles are now kept aside during settling.

      What went away: fork() and the pipe on Linux, F$Fork and the shared block on the F256, the hidden --sztrial option, the "image hides a code label" retry, and the one-source-file limit. Linux and the F256 now run the same sizing code, so every Linux test checks the native path. las shrank by 647 bytes to 46,852. In MAME, level1/cmds takes 914 seconds without an image and 610 with one, against 1,647 and 788 when step 19 began. That is faster than no sizing at all was, since no sizing still read the defs in both passes.

      A shift by twelve

      The new profile of attr still had one line that wasn't about reading source: 18% of every pass in cclsr. That is a routine in CoCoC's C library, not in las. It shifts a number right by a count held in a register. The 6809 has instructions that shift by one bit (lsra, rorb), but none that shifts by several bits at once, so cclsr loops, one bit per turn.

      Who asks for it so often? bank_ptr, the function every symbol access goes through (chapter 9). A handle keeps the block number in its top 4 bits, so the first thing bank_ptr does is h >> 12. DCC compiles every >> of a variable the same way, whatever the count:

      bank_ptr: pshs  u
          ldd   4,s          the handle
          pshs  d
          ldd   #12
          lbsr  cclsr        a 12-turn loop

      But a shift by 12 never needs a loop. Shifting a 16-bit number right by 8 just drops its low byte, which is to say: take the high byte. The other 4 are four lsra instructions:

      bank_ptr: lda   2,s          high byte of the handle
          lsra
          lsra
          lsra
          lsra               block number + 1
          deca
          cmpa  Cur+1,y      the block already in the window?

      So on the 6809 bank_ptr is now written in assembly inside las/bank.c (an #asm block, compiled only for the F256). dco68 had the same fix in step 17. Linux keeps the C version, so every Linux test, including the one-window build, still checks what the function does. The assembly is even 7 bytes shorter than DCC's code.

      In the model, attr went from 27.1M to 20.9M instructions and cclsr from 18% to under 1%. In MAME the 57 level1/cmds took 791 seconds instead of 914 without an image, and 535 instead of 610 with one. The model promised about 20%, and MAME gives 13%. The difference is the time MAME also spends in the disk driver and the system calls, which the model doesn't count. Then you ran the fifth card on the K2: the selftest's eight commands took 95 seconds without an image and 63 with one, against 220 and 102 on the step 16 card, with every module still identical to Linux. The ERROR #115 at the end is still main's grep: alib's FGETS_NOCR puts the caller's old B back over the end-of-file code with its closing puls, so grep exits with a leftover byte. What's left at the top of the profile is reading lines: getsrcline, FindCmd and getc, a function call for every character.

      The install disk: everything a build needs, in one place

      Up to now each test put on the disk only what that test needed, in short paths like /dd/T/J12/src. A disk you work from needs a fixed place for everything, so you never have to think about where a defs file lives. Step 16 builds that disk (harness/card.py build, its own files in install/):

      /dd/CMDS          las llink dcc dcpp dcc68 dco68 make
/dd/LIB           clib.l sys.l cstart.r          (C)
                  alib.l net.l wildbitsl2.l      (NitrOS9 main's libraries)
/dd/DEFS          stdio.h ...                    (C headers)
/dd/DEFS/NITROS9  defsfile os9.d wildbits.d ...  (main's assembler defs)
/dd/SYS           n9mod.opt n9obj.opt make.default helpmsg
/dd/DEVSYS        README  EX (examples)  selftest

      Why the defs get their own directory. CoCoC put a file called defsfile in /dd/DEFS for its RMA-style sources, and NitrOS9's sources say use defsfile and mean a different one. Two files can't share a name in one directory, so NitrOS9's go one level down. Its defsfile is the one from recipes/wildbits/l2, the one main's own build finds.

      An options file instead of a long command. main's build gives lwasm five -D settings and six pragmas. Typed out, a command is longer than the shell's 200-character line, and the C start-up code would split the pragma list at its commas anyway (chapter 11). las already reads more options from a file with --args=, so the disk carries two such files, written from main's own makefiles when the card is built:

      -Dwildbits=1
-DNOS9VER=0
-DNOS9MAJ=0
-DNOS9MIN=0
-Dk2
--pragma=pcaspcr,nosymbolcase,condundefzero,undefextern,dollarnotlocal,noforwardrefmax
-i=/dd/DEFS/NITROS9
--defsimg=/dd/SYS/n9mod.img

      That is /dd/SYS/n9mod.opt, for a module source. n9obj.opt is the same for an object source (section), plus --defs=/dd/LIB/wildbitsl2.l for the system constants a linked program gets from that library. Neither says --lwasm: las sees mod or section and picks lwasm's syntax itself (chapter 3). A new --nitros9 option in las would have done the same job, but it would cost code in a program with 1,851 bytes left, and it would freeze main's settings into las. A file can follow main each time a card is built.

      The last line names a defs image (chapter 9). The first assembly that uses the file records it and the next ones load it, so builds are about twice as fast without you asking for it. If your source defines something before use defsfile, or you add your own -D, the image doesn't fit and las quietly reads the defs as usual.

      Help. NitrOS9's help reads one text file, /dd/SYS/helpmsg. A line @NAME starts the entry for NAME. main's Wildbits disk had no entry for make, so help make said "no help available". The card adds entries for las, llink, dcc, make (from CoCoC's own help) and devsys, replacing any entry with the same name.

      Where output goes. One OS-9 habit catches people. las -o=hello writes hello into the current (data) directory. llink -o=grep and dcc -f=hi write a bare name into the execution directory, /dd/CMDS, as Microware's cc did, because they open the file in "execute" mode. The shell runs a bare command name from /dd/CMDS too, so after las hello.asm ... -o=hello you type /dd/devsys/ex/hello, not hello. The README says this, and for grep it matters: grep alone would run the system's own copy, not the one you just linked.

      The selftest uses only the installed files. It builds and runs hello.c and checks it with dcc -w. It assembles the eight level1/cmds commands, from main now, without an image and then with n9mod.opt. It assembles EX/hello.asm, a small module with a struct, twice to the same file, because you will rebuild into the same name all the time. It assembles main's grep.as with n9obj.opt, links it with the three libraries and runs it on the README. Then it runs make on a C and assembly project and asks help las. card.py check compares every result with the Linux tools, and also compares the Linux results with lwasm's and lwlink's own build of main. So a pass means the F256 built exactly what main's makefiles build.

      In the MAME rehearsal everything passed. The eight commands took 234 seconds without the image and 109 with it, hello.asm and grep together 24 seconds, make 5. One surprise came from grep itself. With -n it numbers the lines it prints, counting in BCD: inca then daa. MAME printed 0040::, a digit of 10 shown as the character after 9. Our 6809 model printed 00044:. Our grep is byte for byte the one lwlink builds, so the difference is in the CPU or in an emulator, not in the toolchain. Your K2 printed 0040:: too, so the real 6809 agrees with MAME and it is our model that differs. Exactly where is still open: an ideal daa after counting 44 lines gives $44, and neither MAME nor the K2 does that.

      On your K2 (the fourth card, 2026-10-12) card.py check said all good: every result equal to the Linux tools and to main's own build. The eight commands took 220 seconds without the image and 102 with it (255 and 120 on the third card), make 7 seconds, and 1,888K stayed free before and after.

      The screen showed one thing the check didn't: ERROR #115 near the end. To find which line, the MAME rehearsal ran again with an echo @n before every selftest line and the shell's error output sent to a file. The error came straight after the line that runs grep. A program's exit status is just whatever is in register B when it calls F$Exit, and grep ends like this (level1/cmds/grep.as):

      EOF                 cmpb      #E$EOF              is error an end-of-file?
                    bne       Error               nope, other error
                    bra       Done                else we're done
Done                clrb                          clear error register
Error               os9       F$Exit              and exit!

      That looks right. The bug is one call down, in the library routine that reads a line (lib/alib/fgets.as):

      FGETS_NOCR:         pshs      d,x
                    bsr       FGETS
                    bcs       bye
                    ...
bye                 puls      d,x,pc

      pshs d,x saves A and B so the caller gets them back, a common courtesy. But on the error path the same puls also puts the old B back, over the error code I$ReadLn had just left there. The carry flag survives (puls doesn't touch CC), so grep knows something failed but not what, and at the end of the file cmpb #E$EOF fails. grep then exits with whatever byte B held before the call: 115 after a match, 110 when nothing matched. The routine documents “Error: B = a non-zero error code”, and its own register save breaks that promise. The fix is to store B into the saved copy on the stack (stb 1,s) before the puls when carry is set. /dd/CMDS/grep, built by lwlink, has the same bug, so the toolchain is not involved. The fix is two lines:

                          bcs       error
                    ...
                    puls      d,x,pc
error               stb       1,s                 return the error code in B, not the saved one
                    puls      d,x,pc              (stb and puls leave the carry set)

      pshs d,x pushed X first and then D, so the stack holds A at 0,s and B at 1,s. Storing the error code at 1,s means the closing puls returns it. Tried in MAME, the fixed grep exits with 0 whether or not it finds anything, and still reports a real error (216, file not found). It is not on the disk: your main clone stays a pristine copy of upstream, and fixes to NitrOS9 go upstream as pull requests. Until then devsys lives with them, and docs/nitros9-fixes.md lists them.

      Trying the fix showed one more thing about NitrOS9's makefiles. A library is built with lwar -c $@ $?. $? means “the inputs newer than the target”, and -c means “create”. So after one source changes, the library is re-created holding only that one member: libalib.a went from 16,289 bytes to 173, and the next link failed with missing PUTS. And make doesn't relink a program when its library changes. That is the second entry on the list.

      A third entry came with your next pull of main. make decides what to rebuild by comparing file times: a target is rebuilt when one of the files its rule names is newer. NitrOS9's rules name only a module's own source, not the defs it pulls in with use defsfile. The pull changed defs/wildbits.d, and make rebuilt nothing that uses it: libwildbitsl2.a stayed at 58,080 bytes, and built from scratch it is 60,858. A build that would track this asks the assembler for the list of files each source read (lwasm can write one) and puts that list in the rule. Until then, the boot disks are built clean after every pull.

      The F256 builds its own tools

      Step 17's goal is the last test of a toolchain: it rebuilds itself. On the F256, make runs dcc on every C file of every tool, and the native llink links the eight programs. If each program comes out byte for byte equal to the one built on Linux, the F256 needs Linux for nothing. harness/native.py self runs that build in MAME and compares all 80 objects and 8 modules. They are all identical now. Getting there took three changes.

      One header first, in every file. A header image (chapter 7) is checked header by header against the text the file really reads, and the check is exact. So every file that uses the image must read its headers the same way. In llink they didn't. misc.c included stdlib.h before rlink.h, rl_02.c didn't include it at all, and lwsel.c included it after. stdio.h leaves out its size_t line when stdlib.h came first, so its text differed between files and three of the seven fell back to compiling without the image, then ran out of memory. The usual rule for precompiled headers fixes it: one prefix header that every file includes first. rlink.h now includes stdlib.h itself, and every file starts with #include "rlink.h". The variables, which rlink.h declares extern everywhere except where MAIN is defined, are now defined in their own small file, llink/globals.c, as las's are. One trap came with the reordering: module.h, now read after rlink.h, set MODSYNC again and would have undone the byte swap Linux needs. It now leaves an existing MODSYNC alone.

      The optimizer's window. dco68 (chapter 7) can only improve code it still holds in memory. It reads instructions into a list, tries its patterns on the newest ones, and when the list is full it writes the oldest out. That list is its window. On Linux it held 32,767 instructions, more than any file has, so it held the whole file. On the F256 it held 300, all that fitted in 64K. One of its improvements is tail merging: when the instructions before a return are the same as some it holds elsewhere, it replaces the copy with a branch to the original. In dcc/DCC/dcc.c Linux's dco68 wrote

       lbra _$26          3 bytes: do what the code at _$26 does
 ...                about 1,700 instructions later
_$26 pshs d
 lbsr exit
 puls x,u,pc

      where the F256's kept its own copy of pshs d / lbsr exit / puls x,u,pc, because the original had been written out long before. Both are correct. But the same source gave different bytes on the two machines, about 310 bytes over the eight tools, and a dcc68 built on the F256 came out at 48,445 bytes, 61 more than a six-block module may have. It wouldn't even load.

      Treating the cause. A smaller window on Linux too would have made the two agree, by giving up the optimization. You asked what it would take to give the F256 the big window instead, since the machine has 2M. Measured in 6809 sizes, a whole file needs up to 106K (dcc68/optim.c: 52K of instructions, 22K of labels, 29K of operand text). That is too much for 64K and little for 2M, the same situation as las's symbol table in phase 8. So it got the same answer (chapter 9, "Moving the table into banked blocks"). Instructions, labels, reference cells and operand texts now live in 8K blocks from F$AllRAM (dcc/COpt/bank.c, a copy of las's). Every pointer between them became a 16-bit handle, and a record is reached through bank_ptr, which maps its block into a window slot. The rule is the one las's symtab.c follows: a pointer from bank_ptr is good only until the next one, so no statement uses two records at once. Comparing two instructions' operands means copying one first. The optimizing algorithm itself didn't change, and that made it easy to check: on 338 inputs (CoCoC's sources and ours), with and without -2, the banked dco68 gives exactly the old Linux output, also in a Linux build that copies a block in and out of one emulated window, where a pointer kept too long reads the wrong bytes.

      Making it fast. Mapping a block costs about 288 µs, so the first version, with one window, would have spent minutes mapping. Three changes brought that down. The numbers are window changes over the 79 files of the cross-build:

      VersionWindow changesWorst file
      One window1,046,99352,292
      List heads in ordinary memory331,04021,408
      Two windows80,6736,912
      Four windows31,4394,251

      The list heads (the start of the instruction list and the 128 label buckets) are touched by nearly every insertion. In a block of their own they forced a switch back and forth all the time, so they moved to ordinary memory, with handles that bank_ptr recognises. Then dco68, whose code takes only two of the eight slots, got four windows. A block already in one of them needs no mapping, and when a new one is needed the window least recently used gives way. A pointer that was safe with one window is still safe with four, so the code didn't change. The last change came from a profile on os9run.py: 37% of the time was in cclsr, the C library's shift. The 6809 shifts one bit per instruction, so DCC calls a loop for h >> 11, eleven rounds at every access. bank_ptr's common case is now fourteen instructions of assembly that take the handle's high byte and shift it three times. On dcc68/codgen.c the 300-instruction dco68 ran 11.7 million instructions, the first banked one 50.5 million, the finished one 27.5 million. In MAME it takes 9 seconds, and building all eight tools takes 784 seconds against 681 with the small window.

      The top slot. The first MAME run hung on the first file, with no output and no error. A debug build that wrote each step to a file and closed it at once (an open file's last sector isn't on the disk until it's closed) showed the first window mapped at $E000. That slot also holds the system's page at $FE00, with the interrupt vectors, and the next interrupt jumped into the new block's bytes. Why $E000? dco68 had grown to 15,866 bytes. A module mapped into two blocks must end by $FD00 ("What fits in 64K, measured", above), so two blocks hold at most 15,616 bytes. Being 250 bytes over, it was mapped at $A000, the top slot stayed empty, and F$MapBlk hands out the highest empty slot. The kernel's F$FreeHB (level2/modules/kernel/ffreehb.asm) already treats slot 7 as taken on one other port (IFNE picothing), but not on the F256. That is entry 5 in docs/nitros9-fixes.md. las never met it because its code fills the top slots. To save bytes, dco68 reads each 2-byte field through a small assembly routine per field offset (4 bytes shorter at each of 148 reads). It is 15,424 bytes now, and at its first block it checks that its own code reaches $E000 (the linker's etext), so a larger build stops with a message instead of hanging. os9run.py now offers the top slot as NitrOS9 does and stops when a block lands there. The model had missed it, which is one more reason MAME is the proof.

      CHAPTER 13Glossary

      AddressSanitizer
      A compiler option that makes a program stop as soon as it reads or writes outside memory it allocated.
      alias
      A second name for the same address. llink adds one when a long name like localtime is wanted and an old library only has its first 8 characters, localtim.
      assembler
      Turns assembly language into machine-code bytes.
      bank switching
      Swapping which block of physical RAM appears in part of the address space.
      big-endian
      Storing a number's most significant byte first, at the lower address. The 6809 is big-endian: the word at 12,s has its high byte at 12,s and its low byte at 13,s.
      binary search tree
      A tree where each node has up to two branches: earlier-sorting names on the left, later on the right. Each comparison rules out a whole branch.
      bootstrapping
      Getting a tool to build itself. The first version has to come from somewhere else, here a cross compiler.
      BSS
      A program's variables that start as zero. The file doesn't store them; the start-up code clears that memory before main runs.
      buffer
      Memory where buffered I/O (C's stdio) keeps a block of a file, so it can read or write a byte at a time without a system call each time. CoCoC gives each file slot one buffer, once.
      cache invalidation
      Deciding when a saved result no longer matches what doing the work again would give. For a defs image: same symbols before the use, same files, same dates and sizes.
      calling convention
      The rules for where a function's arguments and result go. DCC passes arguments on the stack and returns the result in D; a char result is in B only.
      check byte
      Byte 8 of a module header: the first 8 bytes XORed together, with every bit flipped. Lets OS-9 recognise a real header.
      checksum
      A small number computed from a block of data, so that two copies can be compared without comparing every byte: a change almost always changes the number. dcpp and dcc68w compute one per header to tell whether a header image still fits; a CRC (chapter 2) is a stronger kind.
      collision
      Two different names that hash to the same bucket.
      cons cell
      Lisp's building block: a record of two fields, a value and a link to the next cell, from which lists are made. dcc68's member lists (elem) and dimension lists (dimnode) have the same shape.
      CRC
      Cyclic redundancy check: the 3-byte checksum at the end of every OS-9 module. Run over the whole module, CRC included, it always gives 80 0F E3, which is how OS-9 checks a module.
      CRLF
      Windows line endings: carriage return then line feed. Unix uses LF only; OS-9 uses CR only.
      cross compiler
      A compiler that runs on one machine and makes code for another. Our Linux DCC is one.
      defs / defsfile
      Include files full of equ definitions: system call numbers, hardware registers, structure offsets.
      defs image
      A file recording what reading the defs did (symbols, conditionals, counters), so las --defsimg can skip reading them next time.
      dialect
      One assembler's version of the shared assembly language. las supports RMA's and lwasm's, and picks one from the source (chapter 3) unless --rma or --lwasm names it.
      differential testing
      Testing a program by giving it and a trusted program the same input and comparing the outputs.
      driver
      A program that runs other programs in order and passes files between them. dcc runs dcpp, dcc68, dco68, las and rlink.
      dry run
      make -n: print the commands a build would run without running them.
      emod
      Ends a module-format source; the assembler appends the CRC here.
      execution directory
      Each OS-9 process has two current directories: data (for files) and execution (for programs, normally /dd/CMDS). A bare program name runs from the execution directory, and a file opened in "execute" mode, as llink opens its output, is created there.
      exit status
      The number a program hands back when it ends: 0 for success, anything else for failure. On Unix, system() and wait return it packed into a larger wait status; WEXITSTATUS unpacks it.
      exponent bias
      A number added to an exponent so it can be stored without a sign. The 6809's doubles add 128: an exponent byte of 129 means 21.
      expression tree
      How a compiler holds an expression while it works on it: each operator is a node whose branches are its operands, so a + b*2 is a + node with a on one side and a * node on the other. dcc68 builds one per expression (expnode) and frees it after the statement.
      external reference
      A name used in one file and defined in another. Resolved by the linker.
      fixup / relocation
      A place in the code the linker must patch once final positions are known.
      forward reference
      Using a label before it's defined. The reason assemblers make two passes.
      free list
      A chain of memory pieces a program has finished with, kept to be handed out again instead of asking the system for more. dcc68 keeps one for expression tree nodes (freenode).
      handle
      A number that names something without being its address. las gives out symbol handles so the symbols can move between banked blocks.
      hash function
      A calculation that turns a name into a number, always the same number for the same name. Used to pick a bucket.
      heap
      The part of a program's data area handed out while it runs (malloc, sbrk). It grows up towards the stack.
      hidden bit
      The first bit of a normalised mantissa, always 1, so formats leave it out and use its place for something else (on the 6809, the sign).
      ibrk / sbrk
      CoCoC's two ways to get heap memory. ibrk takes it from inside the data area, between the static data and the stack. sbrk asks OS-9 to make the data area bigger (F$Mem) and takes it from above the stack.
      include guard
      A condition at the top of an include file that makes the file skip itself if it has already been read.
      interface
      The set of operations a piece of code offers, with how it works kept private, so the inside can change without affecting callers.
      K&R C
      The C language as it was before the 1989 ANSI standard.
      knock-on error
      An error caused by an earlier error. Fixing the first one makes it disappear.
      least recently used (LRU)
      A rule for what to give up when a small store is full: the item used longest ago, since recent use predicts the next use. dco68 keeps up to four blocks mapped and replaces the least recently used one.
      library
      A bundle of object files (members). The linker takes only the members it needs.
      linker
      Joins object files and library members into one program and fills in cross-references.
      llink
      This project's fork of Microware's rlink, renamed so the two never share a name. Long names, aliases for old libraries, and lwlink's layout when the mainline came from lwasm-style source.
      local label
      A label that only exists within part of a file. In lwasm, a name containing @, valid until the next blank line.
      location counter
      The address where the assembler will put the next byte. Inside an OS-9 module there are two: * for code, . for data.
      LWOBJ
      lwasm's object file format, read by lwlink.
      mainline
      In rlink and llink, the one object file that is the program itself, as opposed to library members. It supplies the module type and entry point, and llink picks its layout from it.
      make
      A program that rebuilds only what an edit affected: a makefile lists targets and what each is made from, and make runs the commands for every target not newer than an input. On the F256, CoCoC's make with rules in /dd/SYS/make.default.
      mantissa
      The digits of a floating-point number: a fraction (on the 6809, between 0.5 and 1) that the exponent scales.
      MMU
      Hardware that maps 8K blocks of physical RAM into the 6809's 64K address space.
      mod
      Starts a module-format source and supplies the header fields.
      module
      OS-9's unit of executable code: header, body, name, CRC.
      native
      Running on the machine it makes code for. A native las runs on the F256.
      negative control
      A deliberate fault fed to a test to show it can detect a problem.
      object file
      Assembled code that isn't finished: it still has names to resolve and places to patch.
      one-pass compiler
      A compiler that reads the source once and writes code as it goes, keeping only what later code may still need (the symbol table). dcc68 is one; Microware's c.pass1/c.pass2 split the work between two programs.
      operator precedence
      Which operators are applied first in an expression, as multiplication before addition in arithmetic.
      options file
      A text file of command-line options that las --args=FILE reads as if typed. The install disk's n9mod.opt and n9obj.opt hold NitrOS9 main's settings.
      overlay
      Code loaded over other code while a program runs, so a program bigger than its address space can run in pieces. Our toolchain doesn't support it.
      padding
      Unused bytes a compiler adds inside or after a structure so its fields line up on convenient addresses.
      peephole optimizer
      An optimizer that looks at a few instructions at a time and replaces known patterns with shorter or faster ones. DCC's is dco68.
      phasing error
      An address that came out different in pass 2 than in pass 1.
      pipe
      A one-way channel between processes: one writes, the other reads, and the system holds the bytes in between. OS-9 provides them through the PipeMan, Piper and Pipe modules, which the F256's boot file doesn't include.
      position-independent
      Code that works wherever it's loaded, because it uses addresses relative to the program counter (,pcr).
      precompiled header
      Headers parsed once and saved in a file, so later compiles load what they need instead of parsing the text again. GCC and Clang have them; Clang loads each declaration only when it is looked up. las's defs image is the same idea for assembler defs.
      prefix header
      One header that every source file of a program includes first, so the header text is the same in each and one precompiled image serves them all. las's is rma.h, llink's rlink.h.
      profile
      A measurement of where a program spends its time, for example the instructions executed in each function. os9run.py --profile makes one for a 6809 program.
      procedure file
      An OS-9 text file of shell commands with the execute attribute. Typing its name runs its lines, like a shell script.
      property list
      Lisp's way of hanging named values on a symbol: get the value for a name, put a new one. dcc68's symnode is a fixed set of properties (type, size, storage class, offset…).
      prototype
      A function declaration that lists its parameter types, so the compiler converts each argument at the call. K&R C has none.
      psect / vsect
      RMA's code section and variable section.
      reentrant
      Code that never changes itself and keeps its variables in each process's data area, so many processes can share one copy. All OS-9 modules are.
      refactor
      Restructuring code without changing what it does.
      reference
      In testing, the trusted program whose output counts as correct. Here, lwasm.
      register tracking
      A compiler remembering what each register holds so it can skip loading a value that is already there. dcc68's version (REGCONTS) compares expression trees; since D53 the value in the register must also be the same width (one byte or two).
      regression test
      A test that checks a change didn't alter existing behaviour, by comparing against the previous version.
      ROF
      Relocatable Object Format: Microware's object file format, made by RMA (and las) and read by rlink (and llink).
      ROF version
      A byte in every ROF header naming the format that wrote it: 0 for Microware's tools, 1 for las. Version 1 adds common blocks, and tells rlink names were kept in full.
      section
      lwasm's equivalent of psect/vsect.
      settling pass
      An extra run of las's pass 2 code that writes nothing, made when a count uses a symbol defined later. It corrects label values until none moves, so the real pass 2 agrees with pass 1 (chapter 4).
      sharding
      Splitting one big job into independent slices that run at the same time, like the 200 native NitrOS9 files over 8 MAMEs.
      shared memory
      RAM that two processes both map into their own address space, so what one writes the other reads. On OS-9 Level 2, one process takes a block with F$AllRAM and tells the other its number; both F$MapBlk it.
      sign extension
      Widening a signed number by copying its top bit into the new high bits. The 6809's sex does it from B into A.
      stack
      Memory used last-in, first-out. Each function call pushes its return address and local variables, and they go when it returns. On the 6809 the S register points to it, and it grows downwards.
      start-up code
      The code that runs before main: cstart.r clears the BSS, copies initialised data, sets up the stack check and the arguments, and calls main.
      static data
      A program's global and static variables, at fixed addresses for the whole run. In a Level 2 C program they start at $0000.
      struct
      lwasm's named record layout: name struct … endstruct defines name.field for each field's offset and sizeof{name}, without reserving memory. The fields' own labels don't become symbols.
      symbol table
      The assembler's list of every name and its value.
      tail merging
      An optimization: when two code paths end with the same instructions, one copy is replaced by a branch to the other. dco68 does it for code before a return or branch, but only among the instructions it still holds (its window).
      threaded tree
      A tree whose unused right pointers point to the next node in order, so it can be walked without a stack.
      trial run
      A throwaway pass 1 that las runs in a separate process to decide instruction sizes before assembling for real.
      uninitialised memory
      Memory a program uses before ever setting it. It holds whatever was there before, which may happen to be zero.
      unsettled
      lwasm's state for a line whose size it can't decide yet. It comes back to the line once more is known, or forces the long form when stuck.
      window
      A slot of the address space where different RAM blocks are mapped in turn. las keeps one for its symbol blocks, dco68 up to four. An optimizer's window is something else: how many instructions it holds at once (chapter 11).
      XOR
      Exclusive or: compares two bits and gives 1 where they differ. Used in check bytes and CRCs.
      zero register
      The 6309's register 0 (code $C in tfr/exg): reads as zero, ignores writes. lwasm accepts it for the 6809 too, where tfr 0,dp clears DP.
