NitrOS9 Level 2 · 6809 · F256

How source code becomes a running program

Compilers, assemblers, linkers, object files and modules, explained with real files from your own trees: a C program compiled by DCC, the object file RMA made from it, and a module built by lwasm.

CHAPTER 01The pipeline

A program goes through several separate tools before the 6809 can run it. Each tool reads one kind of file and writes another. Here is a C program on its way to becoming an OS-9 command:

sum.a

sum.a

sum.r

rlink→

ToolName in DCCJob
PreprocessordcppText substitution. Pastes in #include files, replaces #define names, drops #ifdef'd-out code. Knows nothing about C.
Compilerdcc68Translates C into assembly language. This is where the language rules live.
Optimizerdco68Rewrites the assembly to be smaller and faster, using patterns.
AssemblerrmaTurns assembly mnemonics (ldd, pshs) into machine-code bytes.
LinkerrlinkJoins object files and library pieces into one program and fills in the addresses each piece needed from the others.
LoaderOS-9 itselfReads the module from disk into memory, checks it, and starts it.

Why so many separate programs? On a 6809, a program can address only 64K. One program that did all six jobs wouldn't fit, so each job became its own program, passing files to the next. That's also why a C build creates temporary files. Modern compilers like gcc still use the same stages; they just hide them.

Hand-written assembly skips the first three steps and starts at the assembler. And as chapter 3 explains, some assembly skips the linker as well.

CHAPTER 02What the 6809 actually runs: a module

Every program, driver and descriptor on NitrOS9 is a module: a block of bytes with a fixed header at the front and a checksum at the end. The OS refuses to run anything that isn't a valid module. Whichever tools you use, a module is always the end product.

Here is a complete, real one. This program prints “Hi”. I assembled it with lwasm using the Level 2 wildbits defs:

         mod   eom,name,tylg,atrv,start,size
count    rmb   1                  ← variables: these reserve space,
         rmb   250                ←   they produce no bytes
size     equ   .                  ← total data size = 251
name     fcs   /hello/
         fcb   edition
msg      fcc   /Hi/
         fcb   C$CR
start    leax  msg,pcr            ← address of msg, relative to here
         ldy   #3
         lda   #1                 ← path 1 = standard output
         os9   I$WritLn
         clrb
         os9   F$Exit
         emod
eom      equ   *

And here are the 41 bytes lwasm produced, coloured by what they are:

    Three things to notice

    The header describes the module. 87 CD marks the start of a module. Then: total size, where the name is, type ($11 = program, 6809 code), attributes ($80 = re-entrant, meaning one copy in memory can serve several processes), where execution starts, and how much data memory the process needs. The mod line in the source supplies all of it.

    Variables are not in the module. count and the 250-byte buffer produced no bytes at all. They only set the data size ($00FB = 251) in the header. When the program starts, OS-9 gives the process a fresh 251-byte data area and points register U at it. The code reaches its variables relative to that register. This is how several processes can share one copy of the code: each gets its own data.

    The code doesn't care where it's loaded. leax msg,pcr assembled to 30 8C FA: “X = this instruction's address minus 6”. No fixed address appears anywhere. This is called position-independent code, and OS-9 requires it, because the OS decides where a module goes in memory.

    os9 I$WritLn became 10 3F 8C: the SWI2 instruction, followed by the number of the system call. That's all a system call is. The defs file gives I$WritLn its number.

    Two location counters

    An assembler keeps a location counter: the address the next byte will go to. Inside a module there are two. * counts code bytes, and . counts data bytes. Both start at 0 at mod.

    In hello, count rmb 1 and rmb 250 advance only ., from 0 to 251, so size equ . gets 251, the data area size the header needs. Instructions and fcb/fcc advance *, so eom equ * at the end gets 41, the module's total length. Two counters let one file describe two separate things: the bytes of the module, and the layout of the memory OS-9 will give the process.

    Outside a module there's only one counter, and rmb still writes no bytes. That's how the defs use org 0 followed by a list of rmbs to give names to the offsets of a structure, without producing any output.

    The header check byte

    Byte 8 of the header protects the 8 bytes before it. XOR them together, then flip every bit. XOR compares bits: the result bit is 1 where the two inputs differ.

    ByteRunning XOR
    8787 · 10000111
    CD4A · 01001010
    004A · 01001010
    2963 · 01100011
    0063 · 01100011
    0D6E · 01101110
    117F · 01111111
    80FF · 11111111

    Flip every bit of FF and you get 00, the check byte in hello. OS-9 checks it the other way round: XOR all 9 bytes and the answer must be FF. It's a quick test that a header is real before OS-9 trusts any of its fields.

    The CRC

    The last 3 bytes protect the whole module. A CRC (cyclic redundancy check) runs every byte through a 24-bit shift register: the register starts at FF FF FF, each byte is mixed in by shifting and XORing at fixed bit positions, and at the end every bit is flipped. A single wrong bit anywhere changes the result, and so do most combinations of errors.

    For hello the register ends at CA 6D D8. Flipped, that's 35 92 27, the 3 bytes emod appends. And there's a neat property: run the same calculation over the whole module, CRC included, and the answer is always 80 0F E3, whatever the module contains. That's how OS-9 checks a module when it loads it: it doesn't need to find the stored CRC, it just checks that the total comes out to that constant.

    las computes the CRC while it writes the module in pass 2, byte by byte, so it never has to hold the module in memory. lwasm builds the whole module image first and then computes it.

    CHAPTER 03Three source formats, and why

    Your NitrOS9 and compiler trees contain assembly written three different ways. All three end up as the same kind of module from chapter 2. What differs is how they get there, and the difference is whether a linker is involved.

    Module .asm

    The source writes the module header itself. The assembler outputs the finished module. No linker.

     mod eom,name,tylg,
     atrv,start,size
 ...
 emod
eom equ *

    e.g. scfg.asm, most of NitrOS9

    lwasm object .as

    No header in the source. lwasm writes an object file; lwlink builds the header.

     section bss
buf rmb 80
 endsect
 section code
__start ...
 endsect

    e.g. gfxstatus.as, lib/alib

    RMA object .a

    No header in the source. RMA writes an object file; rlink builds the header.

     psect sum_c,0,0,0,0,0
 vsect
total: rmb 2
 endsect
main: ...
 endsect

    e.g. C compiler output, cstart.a

    The history behind it

    Around 1980, Microware shipped OS-9 with asm, which builds a module directly from one source file. That's the module format. When they added a C compiler, they needed to compile files separately and pull routines from a library, which asm can't do. So they wrote RMA (the Relocating Macro Assembler) and rlink, with their own object file format, ROF. That's the RMA object format.

    Decades later, lwtools (lwasm + lwlink) became the cross-assembler for NitrOS9. It reads the old module format so the existing sources still build. For linked programs it invented its own object style (section) and file format (LWOBJ) instead of copying Microware's. That's the third format.

    Same idea, two vocabularies

    The two object styles express the same ideas with different words:

    IdealwasmRMA
    Code goes heresection codepsect body
    Variables go heresection bssvsect
    Program starts herelabel named __startlast field of the psect line
    Other files may use this nameexportlabel: (trailing colon)
    Object file.o (LWOBJ).r (ROF)
    Library.a (lwar).l
    Linkerlwlinkrlink

    The two binary formats can't be mixed: lwlink can't read ROF and rlink can't read LWOBJ.

    Which one is better?

    Neither. They suit different jobs.

    The object formats win when code is shared or split up: C programs, libraries, big applications. You link only the library pieces you use.

    The module format wins when exact layout matters. A device descriptor is a table of bytes at fixed offsets. A driver must start with an entry table right after the header. With mod you write exactly the bytes you want, in order, and every header field is visible in the source. It's also one step instead of two, which matters when the build runs on a 6809.

    If you use a whole library file in a module, you get the whole library. If you link against it, you get only the pieces you call. That's the main practical difference.

    CHAPTER 04How an assembler works

    An assembler's basic job is a lookup: ldd #3 → CC 00 03. The hard part is labels. Look at this:

             lbsr  printit      ← where is printit? Not seen yet.
         ...
printit  lda   ,x+

    When the assembler reaches the lbsr, it hasn't seen printit yet, so it can't know the address. This is a forward reference. The standard answer is to read the source twice.

    PassWhat it does
    Pass 1Walks the whole file counting bytes, without writing anything. Every time it meets a label, it records the name and its address in the symbol table.
    Pass 2Walks the file again. Now every label is in the table, so it writes the real bytes.

    The two passes must agree on every address. If an instruction comes out a different size in pass 2 than in pass 1, everything after it shifts and the assembler reports a phasing error. That's why ifp1 / use defsfile / endc appears at the top of so many files: read the big defs file in pass 1 only, since its symbols are already in the table for pass 2.

    Choosing instruction sizes

    Some instructions come in several sizes. leax msg,pcr loads the address of msg as a distance from the current instruction. If the distance fits in 8 bits (−128 to +127), the instruction is 3 bytes: 30 8C FA. Otherwise it needs 16 bits and is 4 bytes: 30 8D FF F9.

    For a label defined earlier, the assembler knows the distance and can pick the short form. For a label defined later, a forward reference, it doesn't know the distance yet in pass 1. A two-pass assembler has to guess, and the safe guess is the long form, because whatever it picks in pass 1 it must keep in pass 2, or every address after it would move. That would be a phasing error.

    lwasm avoids the guess by not limiting itself to two passes. It assembles, works out the sizes, and repeats until nothing changes. RMA always uses the long form for ,pcr unless the source asks for the short one with <, even for backward references. That's why las makes some modules a few bytes longer than lwasm does, and why matching lwasm exactly needs extra sizing passes. That's roadmap phase 3b.

    Reading a listing

    This is part of RMA's listing for the C example from chapter 7:

    00008 0000 3440       add:     pshs  u
00010 0005=17fff8              lbsr  _stkcheck
00022 0020 8dde                bsr   add
00024 0024 eda90000            std   total,y
00028 0030=17ffcd              lbsr  printf

    Columns: source line, address, bytes produced, then the source. The = after the address means “this instruction uses a name from another file”. RMA can't know where printf will end up, so it writes a placeholder and leaves a note for the linker. That note is what the next chapter is about.

    bsr add → 8D DE needed no note: add is in the same file, $22 bytes back, so the assembler knew the distance ($DE = −34).

    Files bigger than memory

    The assembler never holds the whole source file. It reads one line into a 256-byte buffer, assembles it, and reads the next. At the end of pass 1 it rewinds the file and reads it all again for pass 2. use files are read the same way while the outer file waits. Macro definitions go to a work file on disk (rma.tmp) and are read back each time the macro is used.

    Output streams too. Pass 1 has already worked out every size, so pass 2 can write the object file's header first and then each line's bytes straight into their place in the file, seeking between the code and data regions as the source switches between them. At the end it goes back to patch one header byte (“assembled without errors”) and writes the reference lists.

    Only a few things must stay in memory until the end:

    Kept in memoryGrows with
    Symbol tablethe number of names, including about 1,600 from the defs
    Reference lists, the object file's “names needed” and “fixups”how often the code uses outside names or needs patching
    Macro names and their positions in the work filethe number of macros, not their length

    So a long program with few names fits easily. What runs out on a 6809 is names and references, not lines. That's why chapter 9 is about the symbol table.

    CHAPTER 05Inside an object file

    An object file is machine code that isn't finished yet. Alongside the code it carries lists: names this file provides, names it needs from elsewhere, and places in the code the linker must patch. Here is the real sum.r that RMA made from the C example, all 158 bytes:

      The four lists

      Header (blue). Sizes: 2 bytes of variables, 59 bytes of code. Notice the type and language bytes are 00 00: this file isn't a whole program, so it doesn't say what kind of module it'll become. Another file (the C startup, cstart.r) supplies that.

      Names this file provides (gold). total at offset 0 in the data area, main at code offset $0E, add at code offset 0. Each has a flag byte saying whether it's code or data.

      Names this file needs (red). printf, used once at code offset $31. _stkcheck, used twice, at $06 and $14. Those offsets point exactly at the placeholder bytes behind the = marks in the listing.

      Local fixups (red, last entry). Code offset $26 is std total,y. The variable total is in this file, but its final place in the data area depends on how many variables other files have. So the linker must adjust this one too.

      An object file is a contract: “here are my pieces, here's what I need, here's where to patch me once you know.”

      CHAPTER 06What the linker does

      rlink cstart.r sum.r -l=clib.l -o=sum does this:

      StepWhat happens
      1. CollectRead every object file listed. Note every name provided and every name needed.
      2. ResolveFor each name still needed (printf, _stkcheck), search the libraries. Take the library piece that provides it. That piece may need more names (printf needs output routines), so repeat until nothing is missing. Anything still missing is an “unresolved reference” error.
      3. Lay outPlace all the code pieces one after another, and all the variable pieces one after another. Now every name has a final offset.
      4. PatchGo through every fixup and write the real offset into the placeholder bytes.
      5. WrapWrite the module header (type, size, entry point, data size) and the CRC. Out comes a module just like chapter 2's.

      Libraries are bundles of members

      A library like clib.l is many object files stuck together. Each one is a member. In step 2 the linker takes whole members, never parts of one. If one member held 20 routines, calling one would bring in all 20. That's why library sources are split one routine per file: lib/alib has bin_hex.as, bin_dec.as, asc_bin.as, and so on.

      Why the module format needs no linker

      A mod/emod file has no needed names (everything comes from the file plus its use includes) and no fixups (the code is position-independent and the data is reached through U). With nothing to resolve or patch, the assembler can do step 5 itself.

      CHAPTER 07The C compiler, step by step

      I ran DCC's Linux build on this file:

      int total;

int add(a, b)
int a, b;
{
    return a + b;
}

main()
{
    total = add(2, 3);
    printf("%d\n", total);
}

      That's K&R C, the style from before 1989: parameter types go on separate lines, and there's no void, enum or const. DCC and the Microware compiler both accept only this older C.

      What dcc68 produced

       psect sum_c,0,0,0,0,0
 vsect
total: rmb 2               ← global variable: 2 bytes in the data area
 endsect

add:
 pshs u
 ldd #_1                   ← stack check: "I need 64 bytes"
 lbsr _stkcheck
 ldd 4,s                   ← a, from the stack
 addd 6,s                  ← + b
 puls u,pc                 ← return, result in D
_1 equ -64

main:
 pshs u
 ldd #_2
 lbsr _stkcheck
 ldd #3                    ← arguments pushed right to left
 pshs d
 ldd #2
 pshs d
 lbsr add
 leas 4,s                  ← pop the arguments
 std total,y               ← C reaches globals through Y
 ldd total,y
 pshs d
 leax _3,pcr
 pshs x
 lbsr printf
 leas 4,s
 puls u,pc
_2 equ -72
_3 fcc "%d"
 fcb $d
 fcb $0
 endsect

      Things to see here:

      It's the RMA object format, with psect, vsect and label: exports. That's why the C toolchain needs RMA and rlink no matter which compiler you use.

      The calling convention. Arguments go on the stack, the result comes back in D. Globals are reached through Y, which the C startup code points at the data area. Hand-written assembly usually uses U for this.

      The optimizer's work. dco68 made two changes. It turned lbsr add into bsr add, a shorter instruction, since add is close by. And it removed ldd total,y, because D already holds the value that was just stored. Small wins like these, made by matching patterns, are all a peephole optimizer does.

      CHAPTER 08Level 2 memory

      The 6809 has 16-bit addresses, so it can see 64K at once. The F256 has much more RAM than that. Level 2 bridges the gap with the MMU (memory management unit): the 64K a program sees is split into eight 8K slots, and the MMU decides which physical 8K block of RAM appears in each slot. You can see the slots in defs/wildbits.d: MMU_SLOT_0 to MMU_SLOT_7.

      Each process gets its own set of eight slots, so each process sees its own private 64K. A process might look like this (illustrative):

      $E000
      program module (code)
      $C000
      program module (code)
      $A000
      unused
      $8000
      window: extra RAM mapped in on request
      $6000
      unused
      $4000
      data area (tables grow here)
      $2000
      data area
      $0000
      data area + stack

      The limit that matters: code, data and stack all have to fit in that one 64K. Level 2 gives each process its own 64K, but not more than 64K.

      The way around it: a process can ask for extra RAM blocks (F$AllRAM) and map one into a free slot when needed (F$MapBlk), then swap it for another. This is bank switching. gfxstatus.as does exactly this to reach the graphics hardware: it maps block $C1 in, reads the colour table, and unmaps it.

      CHAPTER 09Symbol tables: where the memory goes

      Chapter 4's symbol table holds every name the assembler has seen. For NitrOS9 that's mostly the defs files. I measured real F256 sources:

      SourceSymbolsNames longer than 8Bytes of names
      empty program, defs only1,62741513.4K
      scfg.asm1,91149715.5K
      fm.asm2,35360918.6K

      Before you write a single line, the defs alone put about 1,600 names in the table.

      Why long names hurt

      The old Microware tools kept only the first 8 characters of a name. That made every entry small, but MMU_SLOT_0 through MMU_SLOT_7 would all become the same name, MMU_SLOT. The F256 defs have 167 such collisions, so long names are a must.

      The C version of RMA allows 63 characters, but stores every name in a fixed 64-byte box. With 12 bytes of other fields, that's 76 bytes per symbol on the 6809. For fm.asm: 2,353 × 76 ≈ 179K. The process has about 25–30K to spare.

      What one symbol looks like

      Each symbol is one record, a C struct defined in las/rstruct.h:

      struct symblstr
{
    char smbltyp,               /* what kind of symbol        1 byte  */
         locmsk;                /* status flags               1 byte  */
    long s_ofst;                /* its value                  4 bytes */
    struct symblstr *left,      /* tree: earlier names        2 bytes */
                    *right;     /* tree: later names          2 bytes */
    struct ref_xtrnal *reftbl;  /* where it's used            2 bytes */
    char symblnam[64];          /* the name                  64 bytes */
};

      That's 76 bytes, and 64 of them are the name box. Here is a real symbol table. This file (examples/kinds.a) defines one symbol of each common kind:

      locmsk is a set of yes/no flags, one per bit:

      s_ofst is the value: an offset within its section for a label (helper is at code offset $000D, and total sits at data offset $0040, just after the 64-byte buffer), or the number itself for equ and set.

      reftbl points to a list of small records, one for each place the name is used. For printf it says “used at code offset $000A”. At the end, that list becomes the object file's “names this file needs” section, the red part of chapter 5's hex dump.

      Making the record fit the name

      The average name in the defs is 8 characters, yet every record reserved 64 bytes for it. Roadmap phase 2 made each record exactly as long as its name needs, using a standard C trick. The name becomes the last field and is declared as a one-character array:

      struct symblstr
{
    ...                         /* the same 12 bytes of fields */
    char symblnam[1];           /* the name: must stay last    */
};

      When sym_add creates a symbol, it asks for the record's size plus the name's length: sizeof (struct symblstr) + strlen (name). The [1] already covers the zero byte that ends the name, so the name's other characters run on past the end of the declared array, into memory that was requested for exactly that purpose. C doesn't check array bounds, which is what makes the trick possible, and also what makes it easy to get wrong.

      A record now takes 12 bytes plus the name plus 1. Measured on real files:

      FilesBeforeAfter
      376 RMA and DCC-compiled files, the C toolchain's own inputslargest 40.4Klargest 10.7K
      265 NitrOS9 Level 2 files, with the full defsmedian 109Kmedian 30.6K

      The table is about 3.5 times smaller. The C toolchain's files now fit in the 25–30K a 6809 process has to spare, but NitrOS9 files still don't: the defs alone are about 1,500 names. That's the job of the banked blocks and precompiled defs.

      Checking for memory mistakes

      Get the size calculation wrong by a few bytes, and each name overwrites the start of whatever was allocated next. The output might still look right, until it doesn't. The regression test can't reliably see that. A special build can: AddressSanitizer, a compiler option that surrounds every allocation with guard zones and stops the program the moment anything touches one. All 740 regression inputs ran clean under it.

      Then the negative control from chapter 10: deliberately allocating names too short. It needed 4 bytes too short, not 1, before the sanitizer complained. The reason is padding. On Linux the compiler rounds the record up to a multiple of 4 bytes so its fields line up efficiently, and those spare bytes quietly absorb a small mistake. The 6809 has no such rule, so there a 1-byte mistake would corrupt memory, and only on the F256. Knowing where your safety net has holes is part of using it.

      Finding a name quickly: hashing

      The assembler looks names up constantly. Every label is added in pass 1 and found again in pass 2. Every operand that names a symbol (os9 F$Exit, lda #MMU_SLOT_0, lbsr print) is a lookup. That's thousands of lookups per file, so the cost of one lookup is multiplied thousands of times.

      Here are three ways to find one of the 1,664 names in the Level 2 F256 defs, measured on those real names:

      MethodAverage comparisonsWorst case
      Check every name in turn8321,664
      One sorted tree of all names20.753
      64 buckets, a small tree in each (RMA, las)5.114

      Step 1: pick a bucket

      A hash function turns a name into a number, always the same number for the same name. RMA's is about as simple as one can be: add up the character codes, then keep the lowest 6 bits. Six bits hold 0 to 63, so that's the bucket number.

      For F$Exit: F (70) + $ (36) + E (69) + x (120) + i (105) + t (116) = 516. 516 is 8 × 64 + 4, so the low 6 bits are 4, and F$Exit lives in bucket 4. Try any name:

      Why 64, a power of two? Keeping the low 6 bits is the same as taking the remainder after dividing by 64, but it's a single ANDB #$3F instruction. The 6809 has no divide instruction, so a bucket count like 50 would need a slow division routine for every lookup. And 64 bucket pointers take only 128 bytes.

      Once the bucket is known, the search only looks there. Every other name is ruled out without a single comparison.

      How evenly the names spread

      Names per bucket · Level 2 F256 defs, 1,664 names · dashed line: average 26

      Every bucket gets used. The emptiest holds 15 names and the fullest 41, around an average of 26. That evenness is what makes hashing pay off: each lookup searches about 26 names instead of 1,664.

      Adding characters ignores their order, so different names can have the same total. In the defs, 1,337 names share their total with at least one other name. For example, F$Link, SS.DRAM, E$Sect and WIZ_MR all add up to 504, so all four share bucket 56. Two names in one bucket is called a collision. It's normal, and the tree in each bucket sorts it out. On the other hand, names that differ in one character land near each other but not together: MMU_SLOT_0 goes to bucket 31, MMU_SLOT_1 to 32, and so on up to MMU_SLOT_7 in 38.

      A stronger hash (CRC) spreads names a little more evenly, but on these names it still averages 5.1 comparisons, improving only the worst case, from 14 to 12. The cheap hash is good enough because the trees absorb the unevenness.

      Step 2: search the bucket's tree

      Each bucket is a binary search tree: every name has up to two branches, with names that sort earlier on the left and later on the right. Here is bucket 25, the emptiest, built from its 15 names in the order the defs files define them: D.SWPage, D.BTHI, M$IDSize, P$SWI2, P$DeadLk, FMWRIT, V$DESC, E$NoVRef, PD.T0S, PD.DCP, PE.FilNm, FDSL.B, ROMBlock, T1_CTRL, VS_HDAT0.

      Finding PE.FilNm takes 6 comparisons, shown as steps 1 to 6: D.SWPage → M$IDSize → P$SWI2 → V$DESC → PD.T0S → PE.FilNm. Each comparison rules out a whole branch.

      “Sorts earlier” means comparing character codes, as C's strcmp does. In those codes $ (36) comes before . (46), digits come before capital letters, and capitals before lower case. That's why P$SWI2 sorts before PD.T0S.

      The tree's shape depends on the order names arrive. D.SWPage came first, so it's the root. When names arrive already in alphabetical order, each one goes to the right of the last, and the tree becomes a long chain. That's the reason for the occasional worst case of 14 comparisons.

      The algorithm

      Finding a name, as sym_find in las/symtab.c does it:

      1. Add up the name's character codes and keep the low 6 bits. That's the bucket.
      2. Start at the bucket's first node. If the bucket is empty, the name isn't defined.
      3. Compare the name with this node's name.
      4. If they're equal, this is the symbol. If the name sorts earlier, move to the left branch; if later, to the right branch.
      5. If there's no branch that way, the name isn't defined. This spot is also exactly where sym_add attaches a new name.
      static struct symblstr **
bucket (char *name)
{
    register char *p = name;
    int sum = 0;

    do
    {
        sum += *p;
    } while (*(++p) != '\0');

    return &Buckets[sum & (NBUCKETS - 1)];
}

      The tree has one more trick. To print the symbol table and write the object file, the assembler visits every name in order. Normally that needs a stack to remember the way back up the tree, and stack space is precious on a 6809. RMA avoids it with a threaded tree: when a node has no right branch, its unused right pointer points instead to the next node in order. One flag bit, LOC1BYT, says which kind of pointer it is. Walking the whole table is then just following pointers.

      The three-part fix

      PartIdeaEffect
      Compact entriesStore each name at its real length instead of in a 64-byte box.About 18 bytes per symbol instead of 73. No slower.
      Banked tablesKeep the table in extra RAM blocks, mapped in one at a time (chapter 8). Each bucket lives in one block, so a lookup maps at most one block.The table is no longer limited by the 64K space.
      Precompiled defsAssemble the defs once and save the finished table blocks to disk. Later builds load the saved blocks instead of re-reading 1,600 definitions twice.Much faster builds; the defs table is shared and read-only.

      Precompiled headers in modern C compilers use the same trick: do the expensive, unchanging work once and save the result.

      Hiding the table behind an interface

      All three parts change how the table is stored. If code all over the assembler walked the trees itself, each change would mean editing every one of those places, and missing one would break something quietly. So the first step, roadmap phase 1, changed nothing visible. It moved all the code that knows how symbols are stored into one file, las/symtab.c, behind three functions:

      FunctionWhat the rest of the assembler gets
      sym_find(name)The symbol, or nothing if it isn't defined.
      sym_add(name)A new, empty symbol.
      sym_walk(fn)Calls fn once for every symbol, in table order. Used to print the symbol table and to write the object file's name lists.

      That's an interface: a promise about what you can ask for, with the how kept private. Before, the hashing and tree code was spread over labels.c and file_io.c. Now the hashing, the buckets and the tree are invisible outside symtab.c, so compact entries and banked blocks can replace them without touching the callers.

      One detail had to be preserved exactly: the order sym_walk visits symbols in. It decides the order of names in the listing and in the object file, so changing it would change the output, even though no symbol changed.

      CHAPTER 10Testing against lwasm

      How do you prove a new assembler is compatible with an old one? Not by reading a list of features. You give both the same input and compare the output, byte for byte, over as much real code as you can find. This is called differential testing. The trusted tool, here lwasm, is the reference: whatever it produces is correct by definition.

      The harness, harness/lwdiff.py, does this for the whole Level 2 F256 build.

      Getting the real commands

      The harness doesn't guess which files to assemble or which options to use. It asks make. Running make -n -B in the recipe directory is a dry run: make prints every command it would run, for every target, without running any of them. The harness reads that output and picks out the 290 lwasm commands, along with the directory each one runs in.

      Then, for each command, it assembles the file twice: once with lwasm exactly as the build would, and once with las using the same source, include paths and -D definitions. It compares the results and sorts each file into a status:

      StatusMeaning
      MATCHSame bytes as lwasm. The goal.
      DIFFAssembled cleanly, but the bytes differ.
      ERRORSlas reported assembly errors.
      FATALlas stopped early, for example because it couldn't open a file.
      ASSEMBLEDAn object-format file assembled. Its bytes can't be compared directly (LWOBJ versus ROF), so it gets compared after linking, in phase 5.

      First errors and knock-on errors

      The first run, before any changes to las, matched 0 files out of 290. That was expected. More useful is why each file failed.

      scfg.asm produced 1,868 errors, but only the first one matters. Its first error is mod, which RMA doesn't know. Because mod failed, RMA thinks it's outside any code section, so it rejects rmb, lda, rts and everything after as “bad mnemonic”. Those 1,867 later errors are knock-on errors: symptoms of the first one, not separate problems. Fix the first error and they disappear.

      So the report ranks problems by first error. These were the top results in the baseline:

      First errorFilesCause
      bad mnemonic: mod126Module format isn't supported yet. Phase 3.
      bad label74Lines like ;;; ASC_BIN. lwasm treats ; as a comment; RMA only accepts * at the start of a line.
      bad mnemonic: fcb21Data files with no section around them. RMA only allows data inside psect/vsect.
      bad mnemonic: section21lwasm object format. Phase 5.
      can't open "defsfile\r"18These files have Windows line endings. lwasm drops the carriage return; RMA keeps it as part of the file name.

      Why this finds things you wouldn't think of

      Before the harness ran, the compatibility list in the design doc had local labels, fill, ifndef and the shift operators. Nobody listed ; comments or Windows line endings, yet together they stop 97 files. Differences like these are invisible until real code hits them, which is why the test runs over the whole build and not a hand-picked sample.

      Each run also adds a line to harness/reports/history.csv, so the project's progress is a count you can watch: 0 of 290 today.

      Holding the test still

      A measurement only means something if just one thing changes at a time. If the NitrOS9 source changed between two runs, a new match could come from a fix in las or from an edit in NitrOS9, and you couldn't tell which. So the harness doesn't read your working copy of NitrOS9. It assembles corpus/, clones of your devsys branches pinned to exact commits listed in harness/corpus.lock. Moving to newer NitrOS9 is a separate, deliberate step, and every report records which commits it ran against.

      Testing a change that shouldn't change anything

      Comparing against lwasm shows progress, but it can't check a refactor like phase 1, because nearly every file fails anyway. A refactor needs a different question: does the new las do exactly what the old las did? That's regression testing, and harness/regress.py does it. It builds the last committed las as the reference, runs both versions on about 740 inputs, and compares everything they produce: object file, listing, symbol table, error messages and exit code. Any difference fails.

      The inputs are code RMA already handles: 252 hand-written RMA source files, plus 198 C files compiled to assembly by DCC. That's real compiler output, and 430 of these assemble cleanly, so the test exercises working paths, not just error messages.

      Two lessons from building it:

      Prove the test can fail. A test that has never failed might not be checking anything. So before the refactor, I made a deliberate small change (32 hash buckets instead of 64) and confirmed the test caught it: 617 of 740 files changed. This is called a negative control. Only then is “740 of 740 identical” worth something.

      Make sure the test doesn't disturb itself. The first run failed with no code changes at all. The assembler writes macro expansions to a scratch file with a fixed name, rma.tmp, in the current directory. Running the old and new versions side by side in the same directory let them overwrite each other's scratch file. The fix was to give every run its own empty directory. It also revealed a real problem to fix later: two assemblies in one directory on the F256 would collide the same way.

      CHAPTER 11Where this leads

      The project in one paragraph: fork the C version of RMA so it reads all three source formats. Module-format files come out as finished modules. Both object styles come out as ROF for rlink. Fix the name limits in rlink and DCC. Give RMA the three-part symbol table. Prove each step on Linux by comparing its output with lwasm's, byte for byte, across the whole Level 2 F256 tree. Then compile the tools with DCC and run them on the F256.

      The decisions, measurements, open questions and phased roadmap are in docs/DESIGN.md. The latest harness results are in harness/reports/.

      CHAPTER 12Glossary

      AddressSanitizer
      A compiler option that makes a program stop as soon as it reads or writes outside memory it allocated.
      assembler
      Turns assembly language into machine-code bytes.
      bank switching
      Swapping which block of physical RAM appears in part of the address space.
      binary search tree
      A tree where each node has up to two branches: earlier-sorting names on the left, later on the right. Each comparison rules out a whole branch.
      check byte
      Byte 8 of a module header: the first 8 bytes XORed together, with every bit flipped. Lets OS-9 recognise a real header.
      collision
      Two different names that hash to the same bucket.
      CRC
      Cyclic redundancy check: the 3-byte checksum at the end of every OS-9 module. Run over the whole module, CRC included, it always gives 80 0F E3, which is how OS-9 checks a module.
      CRLF
      Windows line endings: carriage return then line feed. Unix uses LF only; OS-9 uses CR only.
      defs / defsfile
      Include files full of equ definitions: system call numbers, hardware registers, structure offsets.
      differential testing
      Testing a program by giving it and a trusted program the same input and comparing the outputs.
      dry run
      make -n: print the commands a build would run without running them.
      emod
      Ends a module-format source; the assembler appends the CRC here.
      external reference
      A name used in one file and defined in another. Resolved by the linker.
      fixup / relocation
      A place in the code the linker must patch once final positions are known.
      forward reference
      Using a label before it's defined. The reason assemblers make two passes.
      hash function
      A calculation that turns a name into a number, always the same number for the same name. Used to pick a bucket.
      interface
      The set of operations a piece of code offers, with how it works kept private, so the inside can change without affecting callers.
      K&R C
      The C language as it was before the 1989 ANSI standard.
      knock-on error
      An error caused by an earlier error. Fixing the first one makes it disappear.
      library
      A bundle of object files (members). The linker takes only the members it needs.
      linker
      Joins object files and library members into one program and fills in cross-references.
      location counter
      The address where the assembler will put the next byte. Inside an OS-9 module there are two: * for code, . for data.
      LWOBJ
      lwasm's object file format, read by lwlink.
      MMU
      Hardware that maps 8K blocks of physical RAM into the 6809's 64K address space.
      mod
      Starts a module-format source and supplies the header fields.
      module
      OS-9's unit of executable code: header, body, name, CRC.
      negative control
      A deliberate fault fed to a test to show it can detect a problem.
      object file
      Assembled code that isn't finished: it still has names to resolve and places to patch.
      padding
      Unused bytes a compiler adds inside or after a structure so its fields line up on convenient addresses.
      phasing error
      An address that came out different in pass 2 than in pass 1.
      position-independent
      Code that works wherever it's loaded, because it uses addresses relative to the program counter (,pcr).
      psect / vsect
      RMA's code section and variable section.
      refactor
      Restructuring code without changing what it does.
      reference
      In testing, the trusted program whose output counts as correct. Here, lwasm.
      regression test
      A test that checks a change didn't alter existing behaviour, by comparing against the previous version.
      ROF
      Relocatable Object Format: Microware's object file format, made by RMA and read by rlink.
      section
      lwasm's equivalent of psect/vsect.
      symbol table
      The assembler's list of every name and its value.
      threaded tree
      A tree whose unused right pointers point to the next node in order, so it can be walked without a stack.
      XOR
      Exclusive or: compares two bits and gives 1 where they differ. Used in check bytes and CRCs.
