# devsys — native NitrOS9 development system for the F256

Goal: build programs on the Foenix F256 itself (6809, NitrOS9 **Level 2
only**) from the same sources lwasm assembles on Linux. Plan: fork the C
version of RMA as the single assembler (named `las`, in `las/`), use DCC as the C compiler, and use ROF
+ our rlink fork (`llink`) as the only native object format.

## Repository

`devsys` is one git repo (branch `main`, remote `origin` = `https://github.com/jfed6000/devsys.git`, set up by the owner 2026-10-15) holding `las/`, `docs/`,
and our forks of rlink (`llink/`, renamed `llink`, D42) and DCC (`dcc/`). No upstream remotes: this is a clean
break, nothing is contributed back. Push `main` only (not work-in-progress branches), and only what the owner
has had committed. Disk images and cards never go in git (`*.dsk` in `.gitignore`). Steps 29/30 (packaging, building NitrOS9 natively) are experiments on a local branch, never pushed until the owner agrees they work. NitrOS9 changes go on branches of the owner's fork `jfed6000/nitros9` (a working clone of it, not `~/projects/wild/main/nitros9`, whose origin is `nitros9project/nitros9`, nor `corpus/`); `nitros9project/nitros9` gets nothing except through a PR from that fork.

## Key files

| File | What it is |
|---|---|
| `las/` | The assembler: our fork of RMA (from upstream commit `e82adeb`, no upstream history kept). Build: `cd las/build/unix && make`. Speed (D64): `FindCmd` matches the first table entry that is a prefix of the mnemonic, so only the order of entries with the same first letter matters (`cmdinit` sorts each table by first letter, stably, at start; a new table must be added there); `getsrcline` reads stdio's buffer directly (`BUFPTR`/`BUFEND` in `file_io.c`, CoCoC and glibc). D66: on the 6809 `search` (`symtab.c`, reads `bank.c`'s `BankCur`/`BankWin`), `fcscan` and `lblcopy` (`findcmd.c`), `lncopy` (`file_io.c`) are assembly with the C kept for Linux; their operands never end in `,y` (`dco68 -2` processes them); `SkipSpac` and `MovLbl` live in `findcmd.c` (no stack checks). Profile with `os9run.py --profile` on te's dco68 output (CR line ends). |
| `llink/` | Our fork of rlink (D13), renamed `llink` (D42) so it never clashes with the original `rlink` on PATH or in `/dd/CMDS`: long names, lwlink's module layout, library choice and module order (`lwsel.c`), chosen from the mainline (`__lwsec`) or forced with `--lwlink`/`--mw`. Internal file names kept (`rlink.h`, `rlink_main.c`). Build: `cd llink && make -f GNUmakefile`. The psect being linked is kept in 8K blocks (`bigbuf.c`, D60: F$AllRAM and a window on OS-9). Its data must stay under 32K or the window has no slot: on the 6809 `grab` cuts records from 1,020-byte chunks (`misc.c`, D66: CoCoC's K&R `malloc` adds 4 bytes and rounds each block; a chunk plus its header is exactly malloc's 1K step). |
| `dcc/` | Our fork of DCC (D18): `CPP` (dcpp), `CC09` (dcc68), `COpt` (dco68), `DCC` (the `dcc` driver, runs `las`). Build: `make -f GNUmakefile` in each. dcc68's symbols and lists are banked (D57, `CC09/symdb.c` on `bank.c`, las's storage): read and write fields with `SG_F(s)`/`SP_F(s,v)`; `SYMP(s)` maps a record, good only until the next access to another symbol or cell; on the 6809 the handle goes in direct-page `symh`. After any change to dcc68: `python3 harness/symcheck.py` (against HEAD's dcc68: plain, `CC09-bankwin` one-window and `CC09-bank16` 2-byte-field builds on ~350 inputs; `--add FILE.c` for more, e.g. jfed's `te.c`). Header images (D50) were removed in D57. dcc68's messages are codes (`CC09/msgs.h`) read from `/dd/SYS/dcc68.msg` (`CC09/dcc68.msg` on Linux, made from `msgs.h`): dcc68 is 448 bytes under 48,384 (D61: no `rewind`, so no `fseek`). Speed (D67): on the 6809 `addin` (`lex.c`), `lnfast` (`get.c`) and `move` (`misc.c`) are assembly; profile with `os9run.py --profile` on a file dcpp preprocessed from its own directory (CR line ends); compare native output with HEAD's native dcc68 (Linux's `ttl` lines differ, `-DFUNCNAME`). `python3 harness/dccdiff.py [--names8]` compiles every CoCoC C source with it and with CoCoC's binaries and compares; `--names8` ignores differences that are only longer names. |
| `clib/` | The C libraries (step 18, D52): our fork of CoCoC's KLibc and SysLib, built by devsys's DCC and las (`cd clib && make -f GNUmakefile` → `lib/cstart.r`, `clib.l`, `clibt.l`, `sys.l`; native/GNUmakefile runs it). Whole names, so D19's aliases are no longer needed; `defs/os9defs.a` is CoCoC's without its unfinished CMOC blocks (installed on the test and card disks). `python3 harness/libdiff.py A.l B.l [--names8]` compares two libraries member by member (CoCoC's `Lib/` is the reference: see D52 for each difference). NitrOS9's `lib/kreiderclib` is a broken disassembly of the same library, not a second one (D68, `docs/nitros9-fixes.md` #6; `python3 harness/kreiderdiff.py` compares it with ours). D67: `putc.a`, `puts.a` (`fputs`) and `printf.a` (`put2file`) take the usual buffered case first (every program's output); a change there changes every native program. |
| `make/` | Our fork of CoCoC's `make` (Tim Koonce's, D45): built for the 6809 by `native/GNUmakefile` (tool `make`); `make.default` holds the devsys rules (`dcc`, `las`), installed as `/dd/SYS/make.default`. Tested by `native.py make`. |
| `las/sizing.c` | lwasm's `,pcr` sizing (D16): pass 1 is the trial (every `,pcr` long), `sz_finish` decides, and settling passes correct the values before pass 2 (D55; until then a child process, D38). Host las prints the settling passes with `LASSZ_TRACE=1`. If a lwasm-mode file grows by a byte or two, `python3 harness/sizediff.py [id]` lists the instructions whose length differs from lwasm's. |
| `harness/lwdiff.py` | Compares `las` with lwasm over the real Level 2 build. Run `python3 harness/lwdiff.py` after every change to `las` or `llink`; `--only NAME --verbose` for one file. `--nitros9 DIR --work DIR` checks another NitrOS9 tree (e.g. `~/projects/wild/main/nitros9`, work dir `harness/out/main-k2`) without touching the corpus results; `sizediff.py` takes the same `--work`. A file whose sizing trial failed is named at the end ("sizing trial failed"). Also replays the build's lwar/lwlink commands and compares linked programs (`--llink`, `--lwlink` options; its links rely on llink's layout detection). Object-format files get the constants library as `--defs`. Report in `harness/reports/`. `harness/rofdump.py file.r` prints a ROF file. |
| `corpus/` | NitrOS9 source the harness assembles: clones of the user's forks (`jfed6000/nitros9`, `jfed6000/nitros9-languages`, branch `devsys`), pinned by `harness/corpus.lock`. Not version-controlled. Set up or restore with `harness/corpus.sh`; `harness/corpus.sh update` moves to the newest `devsys` commits. Don't edit files in it. |
| `dcc/COpt/bank.c` | dco68 keeps the whole file (D51): instructions, labels, reference cells and operand texts are banked records reached by 16-bit handles (`INS`/`LAB`/`CHN`/`ARG`, reads `I_SUCC`…, in `op.h`); one rule: a mapped pointer is good only until the next access to another record. Handles count 8-byte units (62 blocks, D57); operand and label texts are as long as their text (`talloc`/`tfreerec`, change an operand with `setarg`), an instruction's mnemonic is an index into `mnemtab` (`MNEMOF(i)`, a string that stays valid; `mnemix` interns one) (D58). After any change to `dcc/COpt`: `python3 harness/dcocheck.py` (against HEAD's dco68: plain, one-window and four-window builds on ~560 inputs). Native dco68 is three blocks (D61): its code must reach `$E000`, or `F$MapBlk` maps a window over the system page, so `topslot.c` (linked last) pads it with zeros and checks at start; 19,639 bytes, about 4.2K to grow (take zeros away when it needs more; `harness/topslot.py`, run by `native/GNUmakefile`, says how many). Three windows: the module, dco68's data (two slots) and the windows fill the 64K. Speed (D63): no search may walk the whole file (returns have their own list, reference cells are linked both ways, `optim` reads its positions once); keep it so, and measure with `os9run.py --profile` on te (input with CR line ends, output to a file as `dcc` does: `dco68 -2 in out`). D65: label bucket heads are in ordinary memory (`labels.c`), the 6809's record readers test `bankhi` inline and add `bankbias` (`bank_map` sets both), a new action field must be set in `loadfile`/`optinit` (`lastc`, `lskip`), and on the 6809 `igets`/`oputs`/`oputc` (`main.c`) and `parse` are assembly. `#asm` code in dco68's sources goes through `dco68 -2` too, which turns any operand ending in `,y` into an extended address: index Y only as `,y+` and the like. |
| `dcc/CC09/fp6809.c` | Linux dcc68 keeps float/double constants in the 6809's format and builds them with a model of `cfloats.a` (D52), so Linux and the F256 write the same bytes. After any change to it, or to dcc68's constant handling (`lex.c` `number`/`normaliz`, `scale.c`): `python3 harness/fltcheck.py` (native dcc68 on os9run against Linux dcc68; 4,000 generated declarations and edge cases, about 5 minutes). |
| `harness/silent.py` | Step 14's checks (D43, 2 s): a long/double returned in X survives dco68 (`harness/native/longret.c`, also built and run natively by `native.py cc`); las's fatal errors exit non-zero; dcpp out of memory stops `dcc`; concurrent las runs don't share a macro file; dcc68's register reuse keeps char and int apart (`harness/native/regwidth.c`, D53, also run natively by `native.py cc`). Check 6: an unsigned comparison with 0 tests no stale carry (`harness/native/unsgn.c`, D59: dco68's `cmp #0` rules, `dcc/COpt/level1.patterns`). Check 7: dcc68 removes its `cstr.XXXXXX` strings file after a fatal error (D61; Linux and native in the model). Check 8: las reports a symbol never defined in a module (D62: it used to become 0 with exit status 0). Run after changing DCC or las. devsys's `dco68` reads its patterns from `dcc/COpt/level?.patterns` (CoCoC's from `~/.dcc`). |
| `harness/regress.py` | Checks that a change to `las` did **not** change behaviour: compares the working tree with `HEAD` (or `--ref REV`) on ~740 inputs. Must pass for refactors (phases 1, 2, 8, 9). `--skip lwdiff` when a change is meant to alter NitrOS9 results (then check the RMA/DCC differences one by one, as DESIGN.md §8 describes for phase 3). |
| `las/build/stats`, `las/build/asan` | Extra builds of the same source: `stats` (`-DSYMSTATS`) prints symbol table memory, used by `harness/symstats.py`; `asan` checks memory errors: `ASAN_OPTIONS=detect_leaks=0 python3 harness/regress.py --current las/build/asan/las`. Run the asan check after any change to how memory is allocated. For llink, build a sanitizer copy in scratch (`make -f GNUmakefile CFLAGS="-g -m32 -Wno-implicit-int -fsanitize=address" LFLAGS="-m32 -fsanitize=address"`) and pass it to lwdiff with `--llink`. |
| `boot/wildbits/l2/` | The F256 boot disks the harnesses use (D44): `make PLATFORM=k2` and `make PLATFORM=jr2` there build `l2_wildbits_devsys{k2,jr2}.dsk` from NitrOS9 `main` (`~/projects/wild/main/nitros9`; `make N9=DIR` for another tree): that tree's own l2 recipe plus PipeMan/Piper/Pipe and `/nil`. Rebuild after `main` changes, **clean**: `rm -rf .mods .obj .lib` there first (`main`'s makefiles don't track the defs a source includes, and `lwar -c $@ $?` keeps only a library's changed member; `docs/nitros9-fixes.md` #2, #4). The stand-in `rules.mak`, `libs.mak`, `wildbits.mak` let NitrOS9's relative includes find the real ones. |
| `native/GNUmakefile` | Phase 7 cross-build: compiles las, llink and DCC for the 6809 with the host DCC passes, `las` and `llink` into `native/bin/` (`make -f GNUmakefile`; `obj/TOOL.map` + `obj/TOOL/*.lst` give every address a name). DESIGN.md D20, D25. After linking a tool that maps windows (las, llink, dcc68, dco68) it runs `harness/topslot.py`, which fails the build if the module leaves the top memory slot free (D51, D61) and prints each one's room. |
| `harness/native.py` | Runs the cross-built tools on the F256 in MAME (suites `las`, `link`, `cc`, `make`; about 1.5 minutes) and compares with the host tools. Suite `lw` assembles the 200 NitrOS9 module sources natively (`--only NAME`); suite `obj` assembles the 90 object sources, builds the libraries and links the 13 `.as` programs (phase 10); suite `self` (step 17, D51) builds every tool on the F256 with make and native llink and compares each module with `native/bin` (`--only TOOL`); suite `img` assembles level1/cmds without and with a defs image (phase 9). Suite `progs` (step 23, D62) builds jfed's programs from `~/projects/f256/jfed` on the F256 (C with dcc, assembly with las and a NitrOS9 tree's defs) and compares each with the host tools. Run long suites in parallel: `--shard K/N --work DIR --no-build` (run `make -f GNUmakefile` in `native/` first; 8 shards of `lw` take about 22 minutes). Native las options that don't fit the shell's 200-character line go in a file: `las src --args=FILE`. After any change to las, llink or DCC, run **every** suite, not only the one you think is affected (DESIGN.md §8). `--keep` keeps the test image. |
| `harness/card.py` | The install disk and real hardware (K2, SD card; D47): `build` makes `harness/out/devsys_k2.dsk` from the devsys boot image: tools, C libs/headers, NitrOS9 `main`'s defs (`/dd/DEFS/NITROS9`) and libraries (`alib.l`, `net.l`, `wildbitsl2.l` in `/dd/LIB`, assembled by the host las), las options files `/dd/SYS/n9mod.opt`/`n9obj.opt`, help entries (`install/help/*.hp` into `helpmsg`), `/dd/DEVSYS` (README, EX examples, selftest). The owner `dd`s it to the card and types `/dd/DEVSYS/selftest`; `check FILE` compares the card read back with the Linux tools (and with lwasm/lwlink's `main` build); `mame` rehearses the same disk on the Jr2 image (`-Djr2`). `N9=DIR` for another NitrOS9 tree. `build --add FILE` also puts a file of your own in `/dd/DEVSYS` (step 20: `--add ~/projects/f256/jfed/te/te/te.c`). |
| `harness/os9run.py` | Runs one OS-9 program on a host model (6809 from `harness/cpu6809.py` + system calls). ## Every session

**At the start:** read `docs/DESIGN.md` §9 (roadmap) and §10 (open questions)
to see where things stand.

**Before finishing work:**

1. Update `docs/DESIGN.md`: record new decisions with their reasons, tick or
   answer open questions, add new ones, and update the roadmap status column.
2. Update the primer per `docs/learn/GUIDE.md`. If you explained a concept
   to the user in chat, or a roadmap phase finished, the primer probably
   needs a new or extended section. If you changed a hex dump, run
   `docs/learn/tools/build_examples.sh` and
   `python3 docs/learn/tools/check_hex.py`.
3. Add a line to the changelog in `docs/learn/GUIDE.md` if the primer
   changed.

The user wants to understand the work, not just see results. Explain the why,
using examples from their own trees.

## Environment notes

- `LD_PRELOAD` prints a harmless `libgtk3-nocsd` error from every program.
  `unset LD_PRELOAD` before capturing tool output into files.
- The `lwasm` on PATH is a wrapper script that adds relative
  `--map`/`--list` options. For scripted runs use
  `~/projects/coco-shelf/bin/lwasm.orig` with `--output=FILE` and `-I DIR`.
- NitrOS9 lwasm flags are in `corpus/nitros9/rules.mak` (`AS` and `ASM`). The
  Level 2 F256 defs come from `-I nitros9/defs -I nitros9/level2/wildbits -Dwildbits=1`.
- After a fresh checkout of `devsys`, run `harness/corpus.sh` before the harness.
- Native testing (phase 7 on) uses the Wildbits MAME: see DESIGN.md "Phase 7
  test plan" and `~/projects/wild/tempest/docs/port-guide.md` §13. Never modify
  MAME, and mount a copy of a disk image, never the original.
- `las` has two modes: RMA behaviour and lwasm behaviour (`--lwasm`;
  DESIGN.md D12, §4). With neither `--lwasm` nor `--rma`, las picks the mode
  from the source (D40: `psect` → RMA, `section`/`mod` or nothing → lwasm).
  NitrOS9 sources also need the build's `--pragma=` list; the harnesses pass
  it with `--lwasm` (except `native.py lw`, which tests the detection). A change for lwasm compatibility
  normally goes behind `LwasmMode`, so `regress.py --skip lwdiff` (RMA/DCC
  inputs) must stay 450/450.
- Host builds: `las` at `las/build/unix/las`; the unmodified RMA at
  `~/projects/dcc/rma/build/unix/rma` is the reference for "no behaviour change" checks; DCC passes at
  `dcc/{CPP/dcpp,CC09/dcc68,COpt/dco68}` (CoCoC's originals in
  `~/projects/dcc/CoCoC/Source/Compiler/` are the reference for `dccdiff.py`).
